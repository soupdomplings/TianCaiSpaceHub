# 文档规划与维护规范

生效日期：2026-09-30。用户要求：全部二开内容集中登记在 `docs/`，今后的每次开发同步更新文档，并清理过时说明和无用历史内容。本规范适用于功能、修复、配置、协议、桌面交互、打包和上游合并。

## 文档职责

| 位置 | 唯一职责 | 何时更新 |
| --- | --- | --- |
| [docs/README.md](../README.md) | 全目录导航、阅读顺序、资料状态 | 新增、删除、替代或改变文档定位 |
| [二开功能总表](../customizations/README.md) | 当前行为、稳定编号、代码与配置定位、边界 | 新增能力、默认行为/状态/代码入口变化 |
| [二开变更记录](../customizations/CHANGELOG.md) | 每次开发的结果与版本沿革 | 每次开发、修复、移除、上游合并及文档治理 |
| 功能专题 | 使用步骤、行为细节、配置和维护方法 | 对应功能发生变化，直接修订原文 |
| 接口契约 | 两端共同遵守的字段、协议、错误与版本 | 协议变动时，与实现专题同时更新 |
| `docs/upstream-v<版本>-integration.md` | 一次上游整合的来源、差异与保留项 | 每次合入新的上游版本 |
| `docs/development/` | 开发流程、维护标准、清理记录 | 流程变更、历史清理 |
| `docs/releases/` | 单次发布的源码标签、产物、签名及验收边界 | 准备交付及发布状态改变 |
| 根目录 `RELEASE_NOTES.md` / `UPDATE_NOTES.md` | 发布详情摘要 / 最多四条短摘要，供既有 CI 使用 | 准备发版时同步，不替代 docs 记录 |
| 根目录 `AGENTS.md` / `CONTRIBUTING.md` | 强制更新规则的入口 | 约定变更时 |

已有专题路径尽量稳定；新增二开专项文档放 `docs/customizations/`，通用开发流程放 `docs/development/`，跨项目接口契约保持容易发现的固定路径。同一功能只有一份当前行为说明；总表、变更记录和发布说明通过链接引用，不复制整篇细节。

## 每次开发的完成条件

1. 开始前读总表和有关专题，确认版本、默认值、已实现范围和用户新决定；旧方案中的命令、待办和排期不自动成为当前任务。
2. 实施时同步记录改变的行为、兼容决定和限制。新增功能分配新的 `TC-xxx` 编号，已有功能沿用原编号。
3. 交付前修订专题正文，避免把旧行为留在前文、只在末尾追加相反结论。相关协议/API/配置字段、默认值、平台、备份与回滚必须一致。
4. 在变更记录中写本次结果，链接专题；必要时更新功能总表和索引。删除或重命名文档，必须修复引用并登记替代位置。
5. 如果发版，同步 Cargo 版本及既有发布摘要；若只改文档，不自增产品版本，也不覆盖已交付产物。文档整理不授权推送、发布或安装。
6. 核对本次涉及的本地链接、文件名、代码入口与占位示例。交付说明指出文档入口及尚未验收项。

用户决定测试安排。当前用户自行测试：不主动启动 Hub/Codex 交互验证或真实模型调用；开发方可完成必要构建及静态文档核对，并如实登记“待用户验收”。日后用户调整分工时，以最新要求为准；不能为了填满检查表而额外运行测试。

发布安装包按用户最新要求统一由 GitHub Actions 生成，覆盖 Windows 和 macOS；本地不生成发布安装包。交付记录应注明源码提交、Actions 运行、产物文件和哈希。此前本地包作为历史交付保留，不覆盖或冒充本次 Actions 产物。

## 功能专题模板

按复杂度取用下列内容；小修复可更新原章节，无需每次建立新文件。

```markdown
# 功能名称

维护日期：YYYY-MM-DD。适用版本：x.y.z-n。关联：TC-xxx。
实现状态：已实现 / 部分实现 / 计划 / 已撤销。
验收状态：待用户验收 / 已有指定范围的验收记录。

## 需求与边界
用户要解决的问题、已确认决定、平台范围。

## 当前行为与使用
入口、默认值、正常流程、失败和空数据处理。

## 配置与接口
字段、类型、兼容、凭据存储；示例只用占位内容。

## 维护定位
关键源文件、与其他模块的关系、必须保留的行为。

## 迁移与回滚
影响哪些配置或产物、如何撤销、已有备份在哪里。

## 验证与限制
实际构建/测试版本及结果、未执行项、用户待验收项。
```

## 变更记录模板

```markdown
## 未发布 · YYYY-MM-DD · 变更名称

关联 TC-xxx；基线或提交：可定位的提交号，未提交则明确说明。
- 问题与结果：什么情况下原来如何，现在如何。
- 兼容与迁移：默认值、协议/配置改变、保留项及回滚。
- 验证：实际执行结果；未执行或待用户验收项。
- 文档：对应专题的相对链接。
```

未发布的小修复可归并到同一版本，发布前将描述改为最终实现。已发布记录只纠正事实错误，不把后续修复回写成当时已完成；不把上游测试数量算作本地二开验证结果。

## 上游整合与旧内容清理

- 仓库只保留 `main` 主分支，日常二开和上游整合统一进入 `main`；历史版本通过完整二开版本标签及 GitHub Releases 管理，例如 `v0.4.30-2`，不另建版本分支或 release 分支。上游标签/提交仅作为来源记录。推送源码不等于发布版本，发布时按已获授权的范围生成标签、Actions 产物及 Release，并分别记录状态。
- 合并前逐项核对二开总表；记录上游版本/提交、本地基线和合并提交，说明冲突解决后真实保留的行为。
- 上游新增功能标为“上游合入”，本地修改标为“二开衔接”，避免所有功能混记为本地开发。
- 已被现行专题完全替代、仅有空白验证表、依赖不存在目录或含失效操作流程的文档可删除。先迁移仍有效的信息，修复索引和引用，登记删除原因；历史正文可从 Git 恢复。
- 有排障证据、协议取舍或未完成设计价值的资料保留，并在开头写明历史/计划定位、适用版本和当前替代入口；不得继续把当年的临时分支、工作区脏文件或排期写成现状。
- 分支清理必须核对已合并关系、独有提交和 worktree 占用，确认内容完整进入 `main` 后移除多余分支；远端分支另核对服务器实际状态，并用预期提交保护避免删除期间新增的工作。上游仓库的协作分支不因本地二开清理而删除。
- 清理结果写入 [仓库清理记录](repository-cleanup.md)，区分已删除、保留、网络无法确认；不以删除本地跟踪引用冒充删除远端分支。

## 信息质量

当前二开产品名统一为 `TianCaiSpaceHub`，Cargo package 为 `tiancaispacehub`，binary 为 `TianCaiSpaceHub`；Windows 程序为 `TianCaiSpaceHub.exe`，macOS 为 `TianCaiSpaceHub.app`。当前构建和使用示例采用新名称；历史交付包、文件哈希及当时实际执行命令保留原名，注明所属版本。配置目录、`CODEXHUB_*` 环境变量、协议标识和升级身份按兼容规则保留，详见 [品牌与交付](../customizations/desktop-and-packaging.md)。

只写可核对的事实。使用“已实现”“构建完成”“模拟测试通过”“用户验收通过”“已发布”等具体状态，不以单一“完成”替代全部阶段。历史截图、性能估算或某次调试结果不能推导出当前版本已验证。

文档不得新增真实 API Key、ticket、账号令牌、个人配置、私有日志或付款调用记录。源码和同仓库文档使用相对链接；大型构建物、临时日志、截图保留在忽略目录，构建清单仅记产物身份和哈希。
