# Codex 历史会话加载恢复

## 项目卡片已重建后，补回未归属会话（V1.0.39）

删除 `config.toml` 后，Codex 的 SQLite 历史库可能仍有 `projects`、`project_roots` 和会话，但桌面侧栏清单被重新初始化；用户也可能先在桌面手动新建项目并移动了少量会话。初始化或 **ChatGPT / Codex → 接入设置 → 检查与修复 → 删除配置后，项目或分组会话不见了** 的修复操作现在覆盖这两种情况：

- 当前身份必须是 Hub 写入的本机 `ai-gateway` 身份，项目必须只有一个合法本机根目录，项目元数据为空对象，且至少有当前身份的原生用户会话证据。
- 对 `threads.project_id` 为空的会话，只按 `cwd` 与项目根目录的精确路径匹配补回；已经有项目归属的会话不改，名称相同、大小写／别名不明确、跨账户或非 Hub 来源的会话不猜测。
- 侧栏清单为空或缺失时补建项目卡片；用户已经手动重建清单时保留其内容，只执行会话归属恢复。若数据库里同时存在旧项目记录和手动重建的同根目录记录，优先使用当前侧栏中的项目 ID；无法唯一确认时停止处理。账户作用域状态存在时停止处理。
- 恢复会话归属会记录 `hub-project-sidebar-repair/receipt.json`，撤销前核对项目清单及当前归属仍与回执一致；用户改过任一项就拒绝撤销。恢复需要完全退出 Codex，初始化写配置本身仍不因无法恢复而失败。

这项修复只处理当前 Hub 管理身份和精确项目根目录，不迁移会话正文、附件、项目名称、顺序、置顶或信任设置，也不跨账户合并。macOS 代码路径保留但本批未实机验证。

## 删除 config.toml 后找回本机项目（V1.0.37）

适用情形：只删除了 Codex 用户目录中的 `config.toml`，会话库和桌面状态仍在。Windows 桌面版 26.1103.7773.0 的安装资源表明，原生项目、来源目录、会话归属分别保存在 `state_5.sqlite` 的 `projects`、`project_roots` 与 `threads.project_id`。侧栏显示、手动排序和账户相关自定义分组另由桌面状态管理。TOML 中的 `[projects.<path>]` 是文件夹的信任设置，不是项目列表。参见 [OpenAI 项目说明](https://learn.chatgpt.com/docs/projects)和[配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)。

- **还没初始化**：Hub 初始化时，若配置文件确实缺失，优先按最近有效记录取回该 Codex 目录原先的 `sqlite_home`。只接受存在且具备原生会话表结构的本机绝对目录。原先没有指定位置的继续用 Codex 默认位置。初始化后若能读到项目，提示项目数及归入项目的未归档会话数，不表示已经验证桌面可见。增强启动或 WebSocket 设置先创建配置时也沿用相同规则。
- **已经用旧 Hub 初始化过**：进入 **ChatGPT / Codex → 接入设置 → 检查与修复 → 删除配置后，项目或分组会话不见了**。先检查当前库；仅在原位置有证据且与当前默认位置不同时提供修复，退出 Codex 后点修复再重新打开。只在当前配置未指定位置时补一项，现有新库保留，不合并两库。撤销这项修复可退出 Codex 后移除新增的顶层 `sqlite_home` 设置。
- **已有项目但侧栏没有归类**：用原来的账户，在 Codex 左栏选 **整理侧边栏 → 分项目显示**。如历史属于另一模型提供方，先在 Hub 的「Codex 会话管理」核对；仅由用户明确选择需要迁移的会话。Hub 不会改写账户私有分组、置顶、顺序、归档状态或项目信任。
- **无证据时**：同目录 `config.toml.bak` 和 Hub 自己按 Codex 用户目录隔离的位置快照均可能提供线索；没有可用记录时不扫描磁盘、不根据聊天标题或 cwd 猜分组。若找得到自己保留的旧配置，可从中核对原库的 `sqlite_home`。缺库、不可读取、旧版无项目表与可读但为空分别提示。

代码：`src/codex_app_config/history_location.rs` 处理配置缺失、位置快照与手动修复；`src/codex_project_status.rs` 只读统计，不读取对话正文；`src/codex_session_history.rs` 的手动迁移沿用原库位置。实机步骤及验证记录见 [V37 交付](../releases/v1.0.37.md)。下文为先前的会话加载与分页功能。

维护日期：2026-10-29。适用版本：`v0.4.30-9`，关联 TC-006 / TC-007。已实现，Windows 本地测试包由用户验收；具体构建、包身份及验证结果见 [v9 交付](../releases/v0.4.30-9.md)。

## 触发与使用

先完全退出 Codex，再从 Hub **增强启动**。启动时安装内存适配器，点击具体历史会话、实际触发恢复时才等待执行配置；不在启动时遍历、加载全部历史。

本机历史恢复的配置准备返回 `execution-config-loading` 时，沿用 Codex 原有恢复中状态和加载界面，监听原执行配置变化，并以 500 ms 为兜底间隔重读准备结果。等待上限为 15 秒，从首次确认此原因开始计时；后续单次准备读取也受剩余时限限制。配置就绪后由原调用继续恢复，不额外发送聊天、turn/start 或模型请求。计时依赖 renderer 定时器，后台窗口节流或事件循环阻塞可能推迟反馈；它不是网络请求时限。

切换会话或原恢复尝试失效后停止旧等待，检查间隔最多 100 ms；已经发起的配置读取不能强制中断，其迟到结果不会继续恢复。页面请求在切换路由后才失败，或恢复已取消时，也不会再覆盖新会话的错误提示。相同本机会话沿用原 manager 的恢复合并，适配器另合并准备过程及同一路由的重复历史分页请求。每个会话独立，不把其他会话的配置、模型或权限复用过来。

## 分页失败与重试

已适配的历史页面在加载更早内容失败时，即使已显示部分消息，也显示 Codex 原有“无法加载消息 / 重试”提示。点击“重试”会清除当前页错误并实际调用原分页加载器；继续使用原游标、已加载内容和滚动锚点，不通过整页刷新重建历史。重复点击合并到同一次重试，失败后仍可再次点击；不在失败时自动循环拉取全部历史。

15 秒后配置仍不可用，则保留真实 `execution-config-loading` 失败及重试入口，不假造配置就绪。其他读取错误直接沿用真实失败结果，不套用配置等待。原生 transcript 投影状态本身为 `error` 时保留 Codex 原有整页重载按钮路径，该类错误不在本次定向恢复范围；原生时间线的边界分页、缺口重试及锚点补偿继续使用原实现。

## 范围、兼容与配置

- 自动等待仅覆盖增强启动中 `local` host、`view` 来源的历史恢复配置准备；远端、durable、executor、后台 recovery 仍走原流程。Fast/Ultra 可选项未勾选时，历史适配仍独立安装。
- 对用户提供的 Codex `26.1023.51421` 资源，已识别 manager 的恢复产品入口和历史页面。按函数结构、复用变量和唯一匹配核验，不按资源哈希或客户端版本号盲改。布局缺失或歧义时独立跳过，保留原脚本，不阻塞基础增强启动。
- 增强脚本为 v25，模型源码标记仍为 v2，历史源码标记单独为 v1。恢复和分页标记分别记录，历史页面是延迟加载模块，启动时 `retry_adapted=false` 不代表实际访问后仍未适配。
- 不新增用户配置键，不改写本地会话、状态数据库、Statsig 身份或安装 ASAR，不修改原模型、权限、服务档和执行配置的真实性校验。Windows/macOS 共享 CDP 适配，macOS 本轮没有原生构建或验收；不扩展 Linux 支持。

本次诊断确认的直接阻塞是执行配置尚未就绪；同时出现的 Statsig/全局状态 `EBADF` 写入失败，其操作系统根因尚未确认。等待和重试不能保证修复持续的文件写入失败，也不把其他机器反馈的身份错配、`EXDEV` 等错误当作本机已确认原因。

## 回滚与验证边界

完全退出 Codex 后普通启动即不加载内存适配；无需恢复 ASAR 或历史数据。需要返回旧 Hub 时使用保留的旧安装包，已有受管配置的恢复仍遵循 [模型专题](../dynamic-codex-models.zh-CN.md) 原规则。本次未改变配置格式与备份格式。

Windows 构建、离线回归及原始资源静态验证记录见 [交付](../releases/v0.4.30-9.md)。用户需验收首次打开多个旧会话、模型栏恢复、向上加载较早消息、部分消息加载失败后的“重试”、快速切换会话及 Fast 显示。持续错误时保留新版本 Hub 诊断与 Codex 日志；不把静态命中、模拟通过或按钮出现当作真实请求档位已验证。
