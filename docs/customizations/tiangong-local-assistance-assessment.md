## 1. 结论与推荐范围

可行，推荐由 **Hub 提供“本机协助”MCP，配套自动生效的天工协作规则，后端委派本机 Codex 执行**。按用户本轮明确反馈，启用本机协助后，天工应在处理过程中自行判断并调用，用户不必点名 Codex、不必手动选 Skill 或发起交接。天工保留主对话，Codex 处理具体子任务并回传结果，天工继续完成原任务。初期优先复用已接入 Hub 的 ChatGPT(Codex) 执行通道；为无桌面连接场景预留独立 app-server 适配。

这需要新增任务桥接层，不能通过添加一个模型名称或复制 MCP 配置直接完成。MCP 负责调用入口，常驻协作规则负责何时、怎样委派，Hub 负责任务身份、权限、进度、结果、取消及失败恢复。规则可复用 Skill 内容，但必须核对天工实际加载机制；只安装一份需要用户主动选中的 Skill 不满足本需求。纯模型接口只提供额外推理，不自动拥有本机客户端的工具。

建议第一版完整交付“自动识别协助需要、自动委派/等待/有限追问、结果带回天工并继续原任务、长任务取消”。明确点名仅作可用的补充入口，不作为正常流程的前提。默认跟随当前任务授权：用户要分析则只分析，已授权在所选项目修复则可处理；Hub 预先允许的工作区/操作模式是权限上界。第一版不承诺普通 ChatGPT 聊天窗口、ChatGPT Work、Codex CLI 和桌面插件能力完全相同。

### 交付形态、执行端与模型选择

本次讨论的建议交付是 **新版 Hub 测试包，内置“本机协助”服务**，而不是要求普通用户另装一套 MCP 脚本。交付包括：天工可调用的本机 MCP 入口、自动生效的协作规则、Codex 执行适配，以及任务/进度/结果/停止和必要的权限处理。天工侧表现为新增一个 MCP，后端任务由 Hub 管理；不把本项目桥接服务与已移除的官方 `codex mcp-server` 混为一谈。

**首期优先使用已经接入 Hub 的 ChatGPT/Codex App 执行通道**，创建独立协助会话，不把指令发送到用户正在操作的对话。该模式要求 App 正在运行且执行连接就绪；模型接口已接通不等于执行通道已就绪。独立线程/审批归属仍须在实施时验证，目前没有完成互操作验收。独立 Codex app-server 后台模式为后续适配：可减少对 App 窗口的依赖，但工具/插件范围另行核对；不在任务中断后自动换后端重复执行。

**执行端与模型分开选择**：Codex CLI、App 是承接任务的运行方式，不是模型名称。

| 环节 | 谁执行 | 使用哪个模型（建议） |
| --- | --- | --- |
| 主任务 | 天工 Work | 天工当前对话所选模型 |
| 协助子任务 | 首期选定的本机 Codex 执行通道 | Hub 本机协助设置中指定、且在该 Codex 目标实际可用的模型；首次可预填该目标的有效默认配置，创建任务时固定模型/提供方 |

用户已经通过 Hub 分享给 Codex 的天工内置模型，也可以选为协助模型，不强制改用 OpenAI 官方模型或新申请 Key；需满足现有真实协议/工具/压缩兼容和服务端授权。也可为协助指定其他已接入 Codex 的模型。**天工与 Codex 用同一模型时，收益主要来自执行工具、任务上下文和处理方式；不能承诺因此得到更强的模型推理。** 因模型本身能力不足而受阻时，可独立选择更适合的协助模型。

不静默复制天工当前模型到任意 Codex 条目，也不跟随用户其他 App 对话的临时选模变化。选择天工内置模型仍沿原分享/writer、固定来源参数与认证规则；普通渠道仍按各端独立副本/路由处理。模型不可用时明确给配置处理入口，不自动借用同名模型或切换收费来源。普通界面只需“协助方式”和“协助模型”，日常任务由天工自动调用。

## 3. 路线比较

| 路线 | 能解决什么 | 代价/局限 | 建议 |
| --- | --- | --- | --- |
| Skill 指示天工执行 `codex exec` | 最短路径发起一个本机任务 | 容易把运行、结果、超时和审批交给生成的命令；跨轮状态和平台路径难统一 | 可做人工原理验证，不作为普通用户正式入口 |
| **Hub MCP → Codex 执行适配** | 委派本机任务、进度/审批、同任务追问、回传产物 | 新增持久任务和事件路由，须验证天工选工具与 Codex 版本 | **推荐主线** |
| Hub MCP → 普通模型 API | 额外分析、解释、交叉检查 | 本机读写/命令/插件需另行提供，不等于已有客户端执行能力 | 后续可作为“分析助手”，名称与能力明确 |
| 修改天工 Harness/插件加入原生委派 | 可取得可靠父会话、权限与取消事件，做更细的自动求助和对话内进度 | 需维护天工版本/源代码或受支持扩展接口，成本最高 | 第一版验证后再评估，不先改安装包 |

Codex 后端分开适配：

1. **优先复用 Hub 已连接的本机 Codex 通道。** 为协助建立独立线程、事件消费者和审批归属；不要向用户正输入的会话发送消息。先验证现有远控是否允许独立逻辑客户端/线程，不能只编造一个 client key 就声称隔离完成。
2. **预留受 Hub 管理的 `codex app-server` stdio 子进程。** 复用本机合法安装和配置，按安装版本生成/核对协议；不写全局配置。该路径不等于桌面程序已打开，也不自动继承桌面专有浏览器、Office、Computer Use 或应用插件。
3. **`codex exec --json` 可作受限的一次性适配。** 适合固定权限的短任务；需交互审批、长任务和持续追问时优先 app-server。错误/退出不是回退到另一后端重复执行的理由。

官方已移除 `codex mcp-server` 和独立同名二进制，不能把旧教程当作现行推荐。app-server 使用自己的 JSON-RPC，不能直接填入天工的 MCP 命令当作兼容服务。官方迁移页仍标注 app-server 为实验性、不支持生产工作负载：本项目应作为有版本门槛、可禁用的试验能力，先用户验收，再决定稳定交付范围。[官方迁移说明](https://learn.chatgpt.com/docs/mcp-server)、[app-server](https://learn.chatgpt.com/docs/app-server)、[非交互模式](https://learn.chatgpt.com/docs/non-interactive-mode)。

## 4. 用户实际怎样使用

一次设置：在 **天工 Work → MCP** 启用“本机协助”，Hub 自动检查 Codex 安装/执行连接，沿原生 writer 加入服务和自动生效的协作规则。缺少连接时直接给“打开/接入 Codex”的处理入口。用户选择允许协助的项目目录及可执行范围；普通界面以“遇到困难时自动协助”表达，默认跟随任务授权、受 Hub 已授权范围约束。无需每次选协助端或确认是否交接。这些均为建议交互，尚未实现。

日常示例：

> 用户只对天工说：“修好这个项目的启动报错，并确认能够正常启动。”
>
> 天工开始检查 → 发现同类错误连续失败或所需能力不足 → 自动整理必要上下文并调用 Codex → Codex 在已授权项目内定位/处理并返回证据 → 天工接着验证、继续原任务并汇总结果。

过程中可以显示“正在由 Codex 协助定位”的简短进度，无需用户补一句“请调用 Codex”。需要补充信息时，天工可有限追问同一个协助任务，不能把任务 ID 或轮询操作交给用户。处理仍遵守原用户限制；用户只要求分析或明确禁止修改时，子任务同样只读。结果回传改动文件、实际执行的检查、结果及未完成项，天工继续判断和收尾，不能原样转发一句“已经完成”就结束。文件本身在本机生成，不把长文件全文塞回对话。

普通用户不必手填 API URL、JSON、CLI 命令或新的 Key。已有 Codex 配置/身份能否复用由目标执行端检查；需要登录时进入官方流程，不抓 Cookie。使用哪一端的模型配置，就按该端账户/渠道的实际规则和额度执行，不承诺免额外用量。执行发生在本机，不代表模型推理离线。

**ChatGPT 的首期边界：**项目中“ChatGPT(Codex)”的现有执行通道可以作为首个目标；普通 ChatGPT 对话、ChatGPT Work 和桌面专有应用能力不能直接等同于该通道。官方 remote 文档说明桌面远程体验可用宿主工具，但没有由此证明我们新建的 app-server 子进程也具备同样工具。对外按实际探测到的能力展示，不按图标承诺。[官方 Remote connections](https://learn.chatgpt.com/docs/remote-connections)。

## 5. 自动求助应怎样做

自动协助是首期正常路径，启用功能后无需用户再次点名。推荐由常驻协作规则结合清晰的 MCP 工具描述，让天工在以下场景主动调用：

| 建议触发场景 | 自动动作 | 不应发生的行为 |
| --- | --- | --- |
| 同一问题连续两次处理仍失败，且已有有效错误证据 | 汇总失败方法与证据，派一个独立定位/修复子任务 | 换一种措辞无限重试同一方法 |
| 开始处理就能发现所需能力在当前工具范围外，而 Codex 确实具备 | 提前委派相应步骤，不必先故意失败 | 所有任务都无条件转交，或假定 Codex 拥有任意工具 |
| 初步处理完成但关键验证仍失败、原因不清 | 请 Codex 分析具体失败，回到天工完成复核 | 子任务说成功就跳过验证 |

“连续两次”等为建议策略，需实测调优，不能仅靠 HTTP 状态码判定。默认同一个问题只新建一个协助任务，允许自动在该任务内有限补充/追问；达到轮次、时间或无进展上限时如实告知原因，保留结果和用户继续入口。子 Codex 不再反向委派天工或调用同类协助，避免循环。

权限不因自动触发而扩大：当前任务和 Hub 已允许范围内持续执行，不逐次询问“是否请 Codex”；范围之外才需要用户决策。首期普通 MCP 缺少可核验父会话权限，模型传入的权限只能收窄 Hub 已授权上界，不能作为提权凭证。不把任意 401、缺少授权或用户禁止操作解释为可以换一个助手绕过限制。

首期实现机制是 **天工模型按常驻规则自主调用工具**，自动调用能力不应被推迟到后续阶段，但也不能声称模型永远准确识别所有困难。必须以“不提 Codex 名称”的任务验收自动触发、等待、结果接回与继续工作。若要求硬性保证某类失败一定触发，需要后续天工可验证的工具事件/执行扩展；仅靠 Hub 网关不能可靠看到全部工具执行和失败语义，纯 MCP 也不能主动监视任意对话并强行插入任务。

## 6. 最小技术合同与关键断点

推荐在 Hub 新增独立的委派执行服务，MCP 只是前门；持久任务与配置目录隔离，沿现有备份和后改保护管理资源启停。以下工具和默认值都是方案建议，未新增 API：

| 工具（暂名） | 输入和结果 |
| --- | --- |
| `ask_codex` | 明确目标、必要上下文、Hub 预先授权的工作区引用、建议/处理模式；可附已有协助任务引用以追问。快速完成返回结果，否则返回独立任务 ID/查询凭据与等待操作 |
| `wait_task` | 指定本任务并短时等待，返回进度/待用户处理/完成；不新建任务。建议单次等待最多 20 秒，须在各端实际超时内 |
| `cancel_task` | 请求中断本任务，等待终态确认。发出中断与实际已停止分别判断；已发生的文件修改不会自动撤销 |

任务记录应至少包含：实际执行端/线程/轮次、来源资源、工作区与权限范围、幂等键、状态、截止时间、待审批、最终摘要、产物路径和验证证据。状态可为 `queued/running/waiting_user/completed/failed/cancelled/unknown`；这些是后台合同，界面使用简短中文。

必须解决以下问题：

1. **上下文交接。** 天工打包“目标、已尝试方法、相关错误、必要文件、用户限制、验收条件”。MCP 本身不带完整对话；不能为了填上下文遍历桌面历史。工作区建议使用 Hub 已确认引用，模型生成路径只能是请求，不能自己扩大权限。
2. **跨调用存活和身份。** 天工每次调用重建 MCP 会话，任务不能绑定某个 transport/session ID，更不能因 DELETE/关闭会话就杀掉协助任务。只依 MCP 配置凭据可确认配置作用域，不能证明是哪一个天工对话；模型传入的会话字符串不作认证。首期单机同用户/受信作用域，不宣称多用户或严格逐会话隔离；不给模型任意列出/接管所有任务的接口。后续原生适配再提供可核验父会话身份。
3. **长任务和原对话继续。** 短结果直接返回，长结果由天工继续 `wait_task` 等待，同一任务追问。返回任务 ID 后，MCP 服务不能凭此自动唤醒已经结束的天工轮次；若天工不继续轮询，需在 Hub 查看/用户追问，或后续接入原生恢复接口。不能静默向错误桌面对话插入结果。
4. **审批。** 当前审批路由偏向 IM，需要独立接到 Hub 待处理界面；若能可靠映射天工原生审批再集成。模型可请求操作，不能替用户审批自身提权。默认跟随任务授权并受 Hub 预先授权上界约束；明确授权的项目内处理和协助可持续进行，不重复询问是否调用 Codex，额外权限才交给用户。天工的“完全权限”不能不经检查直接映射成 Codex 全盘权限。
5. **重试与防重复。** MCP 调用超时后先查原任务，不能再发一轮等价写操作。`turn/start` 收到应答仅表示开始；只在终态和结果证据齐全后返回完成。Hub 重启或断链先恢复观察，不确定则显示待核对；不自动重放改文件/命令。
6. **并行与递归。** 首期建议每个授权工作区同时一个写任务，忙时排队或让用户处理；读任务也要显式上限。子 Codex 默认不获可再次派发同类任务的 MCP，任务来源/层级另作后台防递归，不能只靠提示词禁止循环。
7. **产物与数据。** 回传摘要、文件/行号、实际检查结果与失败原因；只读允许目录内产物，不让传入路径读取任意文件。认证留在原执行端，不进 MCP 参数/普通日志。输入输出用量只在上游/执行端提供时记录；本功能不改实际请求日志，不把天工主任务与子任务重复统计为同一调用。
8. **能力差异。** 桌面远控与独立 CLI 的可用工具分别核对，特别是浏览器、Office、Computer Use 和已有登录应用。需要前台 Windows 桌面交互时要如实提示占用情况，不宣称所有协助都可纯后台完成。

## 7. 界面和状态推荐

主入口放天工现有 MCP 管理，“本机协助”显示 Codex 是否可用、工作区、自动协助开关和最近任务，避免再造一个复杂管理模块。任务细节默认只展示“正在分析/正在由 Codex 协助/正在处理/等待你确认/已完成/未完成”和结果入口；调用协助本身不新增确认弹窗。

运行图只在发生真实协助后出现关系：**天工 → Hub 本机协助 → Codex**；Codex 经 Hub 模型渠道调用时再显示实际模型/渠道。不能把一次任务状态当成新增模型 HTTP 流量，也不能把独立 MCP 查询结束当成后台任务结束。沿现有延迟暗淡规则展示。

天工内先用真实 MCP 工具结果承载摘要；定制进度卡片取决于宿主扩展支持。Hub 可提供紧凑任务详情、停止和待处理入口，不预先承诺能修改天工原对话 UI。

## 8. 实施顺序与验收

| 阶段 | 交付 | 主要验收 |
| --- | --- | --- |
| A：协议验证 | 合成天工 MCP 调用与 Codex 协议服务、任务/权限合同；确定现有远控能否隔离协助线程 | 每次新连接仍查询同任务、不能串 IM/人工会话、超时后不重复执行、协议不支持明确不可用 |
| B：首个自动协助闭环 | 常驻规则自动选工具 → 建独立 Codex 线程 → 自动等待/有限追问、审批/取消 → 证据回天工继续完成原任务；一键加入 MCP/规则，限次与防递归同时交付 | 用户不提 Codex，只给普通任务；受控能力缺口/重复失败触发实际协助，结果接回并继续验证；普通可解决任务不滥用，原只读限制不丢失，不影响旧配置和任务 |
| C：触发增强与展示 | 如确有需要评估天工原生失败事件接入；Hub 活动图和紧凑任务页进一步打磨 | 规则触发和原生事件证据分别记录，不反复转交、不越过用户约束，子任务运行和工具查询状态正确，用户停止可确认 |
| D：扩展端 | 各端采用真实执行接口逐一适配 | ChatGPT Work/其他端能力先核实；没有执行接口的端不以模型 API 冒充完整客户端 |

建议首期完成 B 的真实闭环后再决定 C/D，而不是先支持许多只会显示名称的客户端。开发量的主要部分是任务生命周期/隔离和审批，不是 MCP 表单；未做真实原理验证前不承诺固定工期。

离线回归拟覆盖：严格 MCP 握手/目录、每次新会话的任务持续性、父任务上下文缺失、非法路径/后改、错任务凭据、重复/取消/断链/重启、Codex 乱序事件和身份、模型/提供方变化、两种权限模式、审批拒绝、并行写入、防递归、结果限长/产物访问、秘密脱敏、现有 IM/模型/Skill/MCP 不变。Windows 优先；macOS 需另行原生构建和用户验收，不扩展 Linux。

本轮只做源码与官方文档评估，没有执行上述回归，没有新 MSI，没有真实客户端或模型调用。888 项产品输入及原文档快照见本轮证据目录；文档变更不提升版本，后续功能实现另按用户授权与届时最新版本安排。

评估收尾观察到工作区内 `src/gui/clients.rs`、`src/gui/codex_models.rs` 与开工哈希不同；本轮工具只修改四份文档，未修改或回退这两处并发源码变化。当前工作区与评估开工快照不声明逐字节相同，观察记录见 `verification.json`；不能把之前 MSI 身份直接用作当前源码身份。
