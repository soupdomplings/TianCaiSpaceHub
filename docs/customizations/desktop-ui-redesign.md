## 先看结论与原型

推荐保留 Rust + wxDragon，先重构信息架构、页面容器、任务编排和公共控件。把 Hub 定位为“选好模型，就能打开客户端；需要时再接聊天和工具”的桌面连接中心。日常打开客户端是一条主线，模型来源、客户端配置、外部消息和 MCP 各自有明确归属。

- [独立原型](../mockups/desktop-ui-review/index.html)：直接用浏览器打开，无需 Hub、构建或网络；全部为合成数据。
- [原型使用及验证记录](../mockups/desktop-ui-review/README.md)：推荐查看顺序、演示边界与窗口核对结果。
- [现有界面与操作完整盘点](desktop-ui-inventory.md)：现入口、操作、重复点、断点和建议去向逐项对照。

建议先评审“概览曲线 → 对应请求”和“WorkBuddy 模型 → 用于天工 → 独立调整 → 来源选择同步”两条路径，再评审模型来源、Codex 设置、Skill/MCP、聊天和维护；客户端概览改为连接图，管理开关直接使用。原型中的聚合数据、复用记录、差异和设置是设计建议，不代表当前后台已提供对应新接口。

第 2 稿按用户反馈补齐 **完整状态概览、ChatGPT 接入设置、Skill 管理、通用 MCP 管理**。这改变首稿导航建议，不改变产品现状；详见 [新增管理能力与设置规格](desktop-capability-management.md)。Skill 与通用 MCP 属于新增规划，不能套用现有 Dumpling 的三端支持结论。

## 2. 现有结构为何需要整体调整〔事实与判断分列〕

当前结构由代码还原，**不是运行截图**：

```text
原生菜单：文件 / 语言 / 主题 / 网络 / 帮助
固定状态概览：客户端入口 → 本机服务 → IM
Notebook：Codex | WorkBuddy | 天工 Work | 大模型 | 聊天工具 | 请求日志 | 可选 MCP
页内表单与按钮；另开渠道编辑、扫码、历史、日志详情、修复等窗口
底部版本状态栏；托盘：打开 / 退出
```

| 代码确认的现状 | 设计判断与影响 |
| --- | --- |
| 全局概览固定在 Notebook 上方，前三页切换概览类型，公共页保持上一个客户端视角 | 看渠道或日志时仍占用高度，且概览含义依赖前一次导航。建议把全局服务缩成状态条，完整链路保留在“概览 → 运行状态”及客户端页 |
| WorkBuddy/天工各有启动、刷新、撤销、保存、删除并列按钮 | 查看、使用、编辑、恢复的操作层级相同。建议默认列表用于使用，编辑时才出现保存，维护时才出现撤销/删除 |
| 来源渠道、Codex 可见模型、客户端专用副本是不同编辑区 | 这是合理的业务分离，但当前需要用户记住跨页顺序。建议用“保存后继续给某客户端使用”的上下文衔接保留分离 |
| 当前日志页有 13 列、日志/详情开关、清理旧日志/全部日志；GUI API 固定读取最近 200 条，未见独立筛选栏 | 不能把“已有成熟筛选界面”写成事实。建议首屏保留 6 个信息组，增加当前已加载范围的明确筛选；全量筛选/分页需另补后端 |
| `onboarding.rs` 是各 IM 平台的接入引导，没有统一首次使用向导 | 新方案增加面向任务的首次入口，保留原扫码、轮询、超时与取消规则 |
| theme 已有 system/light/dark；原生 appearance 在窗口前设定，切换提示重启 | 不重建一套主题系统；扩展既有 tokens。原型即时切换仅便于评审，不据此承诺产品即时换肤 |
| MCP v12 已移除手工检查、刷新和单独上游检测 | 复用其主操作。不要因本轮统一样式把已精简入口加回来 |

导航不是单纯换一个控件：`gui.rs` 的 `CODEX_TAB_INDEX=0`、`WORKBUDDY_TAB_INDEX=1`、`GMCLAW_TAB_INDEX=2`、`REQUEST_LOG_TAB_INDEX=5`，`ClientOverviewUi::select_page`、`on_page_changed` 的日志计时器，以及 MCP 动态显示/隐藏都相互关联。必须一起替换为有类型的页面目标和可见生命周期，不能改顺序后继续依赖这些数字。

## 3. 推荐信息架构〔设计建议〕

左侧固定导航，正文只呈现当前任务。侧栏按客户端和共用能力分组，最多两层，不把所有维护项塞进一个“更多操作”。

```text
概览                           运行状态（默认，完整链路） / 使用统计
天才小分队                     登录 / 账户 / 密钥 / 使用记录 / 条件组织与扣费 / 模型 / 充值订阅 / 账户工具
客户端                         分组标题，不再多一层无意义中转
  ChatGPT(Codex)                状态概览 / 模型 / 接入设置 / Skill与MCP / 历史与维护
  WorkBuddy                    状态概览 / 模型 / Skill与MCP / 维护
  天工 Work                    状态概览 / 模型 / Skill与MCP / 聊天衔接与维护
模型与渠道                     模型列表与来源 / 账号与渠道 / 编辑
聊天接入                       平台账号 / 接入向导 / 使用与权限说明
Skill 管理                     资源列表 / 各端使用开关 / 添加与维护
MCP 管理                       工具服务 / 可选 Dumpling-MCP 环境与连接
请求记录                       统计筛选下钻 / 请求分页 / 客户端与实际上游详情
──────────
设置                           外观语言 / 网络与本机服务 / 系统集成 / 可选功能
帮助                           按当前任务查帮助 / 版本与诊断导出
```

建议 Skill 与通用 MCP 管理固定可见；`showDumplingMcp` 仍默认 `false`，将发现入口移至“设置 → 可选功能”，建议它只控制 MCP 管理中的 Dumpling 来源，旧帮助入口作为过渡别名。隐藏不影响通用服务库，也不断开、注销或清理已有连接。此入口语义调整尚未实施；原型初始显示 Dumpling 供评审。

普通来源改称“模型来源”并保留“渠道”次级说明。**不把普通来源和客户端专用副本合并为一个可编辑对象**：来源页默认列普通来源；通过用途视图可查看专用条目；运行图中的渠道操作直达该条目的渠道详情，不跳客户端顶层，也不借用同名普通来源。既有专用渠道的启停、低层编辑和删除放入该条目的“高级渠道管理”，显示影响范围并继续调用原接口，不无意移除这项已有能力。

全局本机服务使用一条带时间/错误入口的状态提示。客户端概览用连接图汇总模型、扩展与执行；各项证据在详情中分别判断。模型/Skill/MCP 日常只呈使用选择，公共页面不继承某个隐形的“当前客户端”。

## 4. 关键页面规格〔设计建议〕

| 页面 | 首屏布局与唯一主操作 | 编辑/维护位置 |
| --- | --- | --- |
| 概览·运行状态 | 已打开/在用客户端 → Hub → 使用中模型 → 使用中渠道，同屏展示；无人打开时仅 Hub；Codex 执行状态并入本端行；聊天/扩展用紧凑摘要 | 点选高亮与行详情；进行中请求（N）列出完整路由的请求；渠道带精确身份直达配置；闲置配置从客户端模型页进入 |
| 概览·使用统计 | 请求、输入用量、输出用量、完成率；缓存包含在输入中，不单列；时间/接入点/来源/模型筛选；Token/请求趋势、分布、结果 | 曲线时段/分布/结果进入同范围请求；未知用量、归属和费用不补造；统计聚合 API 尚未实施 |
| 天才小分队 | 未登录主操作为登录，账号页内导航按站点权限及开关；API 密钥直接导入 Hub | 组织内部、充值/订阅、资料与工具复用站点原页；原一次性导入/配置保护不改，账单与本机统计分开；见 [专题](tiancai-squad-account.md) |
| 客户端·状态概览 | 标题旁显示短状态；客户端 → Hub → 模型连接图，下排 Skill、MCP、聊天与执行，可点节点操作 | 图节点展开具体证据/恢复，模型与维护各有子页；不再逐行状态卡 |
| 客户端·模型 | 已管理条目、来源、参数；“从我的模型加入”；条目可用于其他客户端 | 各端独立调整；既有手动编辑、协议/新增来源及草稿继续保留，不复制其他端专用身份 |
| Codex·模型 | 普通路由与可见模型；候选来源方案不代表锁定单一来源；“从我的模型加入” | 手填/内置/渠道同步/远端目录收纳到可展开目录维护，保存可见列表仍独立；无路由先选普通来源 |
| Codex·接入设置 | 受管初始化/更新、增强启动说明、WebSocket、App/VSCode/CLI 状态 | 账号登录直达模型来源；受管恢复在历史与维护。现有设置不再只用说明弹窗占位 |
| 客户端·Skill与MCP | 本端资源列表，直接“使用中 / 未使用”开关与“添加” | 与管理页共享目标身份和真实配置结果；依赖/授权/冲突才展开 |
| Skill 管理 | 紧凑资源列表、各端使用开关；“添加并使用”一次选择内容与客户端 | 点击内容可看来源/依赖；内部读取、适配与保护自动完成，必要决策才确认；新规划 |
| MCP 管理 | 工具服务与可选 Dumpling；服务列表与各端使用开关 | 真实适配按传输/认证/作用域开放；Dumpling 保持原认证、桥接及一次连接并检测；新规划单独标注 |
| 模型与渠道 | 我的模型只列模型与来源，不分配客户端；账号与渠道按现有八类厂商展示来源表单及专用渠道详情 | 复用、来源更新和参数调整分开；账号/API、目录、别名、权重/兼容项等既有能力保留 |
| 聊天接入 | 账号列表、平台、状态、可用执行端；“添加聊天接入”先选平台 | 账号范围管理和删除归所选账号；新建/恢复会话继续在 IM 完成。Hub 不伪装已有统一会话/任务控制台 |
| MCP·Dumpling | 环境列表 + 当前环境；已授权时直接看到客户端与“连接并检测”；工具数量/目录受限状态 | 初次保存、认证挑战、连接确认按步骤展示；环境管理和所选客户端维护分别成区，断开与删除整环境的范围不同 |
| 请求记录 | 与统计同一范围；分页、搜索、终态筛选；时间/归属、模型/来源、结果、用量、耗时 | 第三稿对全部合成记录筛选，不截取最新 200 条再称全量；产品需分页/聚合接口。原头/体/SSE/响应/错误保留在实施回归范围，原型仅示意主要字段 |
| 设置与帮助 | 左侧分组，右侧单列设置；保存反馈就近显示 | 主题/语言重启语义、本机连接模式、出站代理、网页导入注册、诊断导出、托盘解释和关于均保留；不恢复已取消的自动更新入口 |

客户端编辑器差异不能被公用布局抹平：WorkBuddy 思考强度默认 `high`，协议在允许条件下可调；ChatGPT 账号来源锁 Responses。天工思考强度默认自动，输出 `8192`、温度 `0.7`、温度策略自动；协议只读、不引入默认模型控件、GUI 保存继续 `makeActive=false`；天工来源继续排除 ChatGPT 账号。模型列表可见、能选 `max` 仅说明配置项存在。

## 5. 核心任务路径与减少点击的具体方式〔设计建议〕

点击数仅计算按钮/导航动作，不包含文字输入、列表选择、系统授权、运行中客户端退出确认；不是已实现性能承诺。

| 场景 | 当前路径〔核对〕 | 建议路径与自动衔接 |
| --- | --- | --- |
| 日常使用 | 找客户端页，再找启动按钮 | 客户端工作区固定“打开”；概览默认运行状态，已打开客户端保留就近入口；已关闭客户端从侧栏进入；不暗中创建会话或发送模型请求 |
| 复用已配模型 | 另一个客户端重新选来源、模型和参数 | 当前条目“用于其他客户端”→ 选目标；兼容新增直接保存。目标已知则省选择，已有差异保留目标参数优先；不借用别端专用路由 |
| 新接 WorkBuddy/天工 | 大模型新增/保存 → 客户端页 → 刷新 → 新增/选来源/模型 → 保存 → 启动 | 客户端页或“配置客户端”→ 选已有来源或添加来源 → 配置模型并“保存并继续” → 打开。跨页返回保留草稿，页面自动只读加载；用户无需“刷新” |
| Codex 首次使用 | 来源配置、可见列表、初始化、退出、增强启动分散 | 客户端向导中依次“选择模型 → 确认接入 → 打开”；无有效来源才补来源步骤。配置和可见模型仍分别提交；客户端运行或需更新时明确停在原有预检，不强杀进程 |
| Skill / 通用 MCP 使用 | 当前 GUI 没有统一跨端管理入口 | 已有内容直接打开目标端开关；新内容选来源和客户端后“添加并使用”。无争议自动完成读/适配/保护/保存，依赖、授权或冲突才决定；失败保留旧选择。见 [管理规格](desktop-capability-management.md) |
| 来源修改后同步 | 改来源，再逐客户端重选/保存，缺少影响提示 | 来源保存结果列出使用它的独立条目，“查看受影响条目”；逐条比较并确认更新。新增只读差异摘要后才显示“有更新”；不后台批量改副本 |
| MCP 日常连接 | v12 保存环境 → 登录/授权 → 选客户端 → 连接并检测 | 已保存且授权有效时维持一次“连接并检测”；初次配置用步骤区引导，保存成功继续到认证。认证方式和真实挑战不省略 |
| 模型不在路由内 | 客户端报 422，用户自行找来源/条目 | 本次日志/客户端页提供“检查此模型配置”，带入口和条目身份进入对应编辑器；不能仅凭模型名选择别的来源 |
| 并发修改 | 当前原生错误提示刷新重试 | 保留草稿，显示“查看变化”；比较原值、最新值、本次草稿，重新确认目标，再经当前 revision 保存；不靠换 token 强行重试 |

用户选择使用后，程序自动读取、核对、转换和受保护保存，成功就近反馈；需要决策或继续操作时才展开。多个后台写入没有统一事务，异常必须说明已完成范围。例如来源保存成功而客户端保存失败：保留新来源和客户端草稿，提供“继续配置客户端”，不删除已成功内容，不重复执行结果未知的写入。

手工刷新从日常主路径退出，放在明确“重新读取配置”的维护入口；进入页面、成功保存/删除/撤销后自动读取。表单有草稿时只提示“外部配置已变化”，不以刷新覆盖输入。异步结果绑定页面目标、条目、草稿代次和请求代次，取消/切换后丢弃迟到结果；忙状态只锁当前任务依赖，不冻结整款产品。

## 6. 状态、错误和恢复〔设计建议〕

下面是内部状态证据和必要错误的规格，不把它们排列成普通用户必须完成的步骤。模型/Skill/MCP 管理只呈“使用中 / 未使用”，运行概览通过图节点与短状态表达当前情况；需要时可打开证据详情。

| 维度 | 建议普通文案 | 可用证据与边界 |
| --- | --- | --- |
| 配置使用 | 使用中 / 未使用；异常时读取失败或需处理 | 读取原生配置后判定；忙状态不提前翻转。客户端安装、运行与请求另有证据，不在普通管理页列多阶段进度 |
| 本机服务 | 运行中 / 正在启动 / 无法使用 / 状态过期 | 当前 daemon 身份及状态；不能用端口可连替代身份验证 |
| 客户端到 Hub | 等待客户端请求 / 已收到本机请求 / 客户端未运行 | 使用既有客户端特定证据；天工有效本地请求可证明到 Hub，即使上游失败；没有等价证据的客户端不照抄 |
| 上游 | 目录已获取 / 尚未检测 / 最近请求失败 | 目录成功不证明推理可用，不自动为显示状态发起模型调用 |
| 实际调用 | 最近一次完成 / 失败 / 中断 / 结果未知 | 只引用对应入口/条目、本轮可关联的真实请求；过去单次成功不证明所有模型能力；普通入口无法证明来自哪个进程时明确普通入口 |
| 外部消息 | 平台账号已接入 / 执行端待准备 / 可接收任务 / 待审批 / 结果未知 | 平台、执行端与运行/审批身份分别核验；WorkBuddy 不可选外部执行，Telegram 不显示天工作为可用执行端 |
| MCP | 使用中 / 未使用；需要时显示授权或信任入口 | 后端及诊断详情保留认证、检测、目录、调用各自证据；普通页面不要求逐项检查。Dumpling 保持原连接并检测 |

运行状态使用多客户端纵列汇入 Hub，再路由到使用中的模型 → 使用中的渠道。只显示已打开/在用客户端与进行中模型，没有活动客户端时仅显示 Hub；旧矩阵改成行详情，Codex 执行状态收进本端行，不保留重复卡片。入口、模型、实际来源与条目身份一致，普通入口保持客户端未知；终态移出图并保留请求记录，失败可从客户端详情或日志检查来源。首字只从统计移除，实际日志的采集、列表与详情保留。原型使用合成观察，原生需验证实时证据、新鲜度、绘制性能和减少动态效果支持。

第一阶段只能展示现有字段有证据的状态。统一的 `observedAt/source/capability`、精确来源差异、可关联客户端标签等若当前响应缺失，需要新增**可选只读字段**，旧服务缺失时显示未知，不从现有字符串猜成功。

| 问题 | 主恢复操作 | 次级说明与禁止的自动动作 |
| --- | --- | --- |
| 本机服务不可用 | 重新连接本机服务 | 显示自动恢复进度；失败后“本机连接设置”，诊断详情折叠；不每个卡片弹一遍错误 |
| 模型未配置/条目停用 | 检查此模型配置 | 目标必须保留普通/WorkBuddy/天工及 entryId 范围，不跨入口回退 |
| 地址缺版本 | 延续 v13 自动处理 | 原地址优先、同源一次、有效成功才保存；两次失败保留原地址错误，界面不另加手动“补 /v1”按钮 |
| 账号或 MCP 授权到期 | 重新登录/授权 | 回到原环境和客户端；保留服务端身份校验，不沿用上一代旧成功状态 |
| 并发配置变化 | 查看变化并重新确认 | 保留草稿、最新快照和目标身份；删除/改名后的对象不能以旧 ID 自动重建 |
| 客户端尚未退出 | 退出后继续 | 自动只读检测退出状态，提供取消；不结束用户任务 |
| Codex 历史未加载完整 | 重试当前页 / 查看恢复指引 | 延续 v9 按需等待、分页重试与取消合并；持续 EBADF 明确尚无根因修复，不增加“彻底修复历史”按钮 |
| 修复/备份恢复遇后改 | 查看冲突与备份 | 继续原预检和受保护恢复；不扩大修复范围、不静默覆盖 |
| 任务中断且可能已经执行 | 查看客户端并核对结果 | 未核对前不能“重试任务”；按既有规则显式新建，不以切换或断开冒充取消 |
| 工具目录超限 | 继续使用并查看目录说明 | 已连通、数量未知与认证失败分开；不请求完整 schema 堵塞 GUI |

普通错误区域采用“发生什么 + 对当前任务的影响 + 一个继续操作 + 可展开技术详情”。字段错误就近显示，避免关闭后才能修改的二次弹窗；写入确认、真实认证挑战和危险范围确认仍用模态窗口。不会把所有失败改成含糊的“稍后重试”。

## 7. 视觉、布局与弹窗规范〔设计建议〕

方向：浅灰工作台、白色内容面、克制的青蓝主色；深色为蓝灰底和更浅的主色。减少粗框、大块状态底色与长段常驻说明，让标题、间距、表格和一个主按钮形成层次。继续使用品牌已有的透明线条客户端图标，不另换 logo 体系。

| 项目 | 建议规格 |
| --- | --- |
| 字体 | Windows 使用系统 UI 字体并允许中文回退，macOS 使用系统 UI 字体；原生以 point size 设置。页面标题 18 pt、分区 11–12 pt、正文 10.5–11 pt、辅助 9–10 pt；最小正文不靠缩字号解决拥挤。HTML 的 14px 正文仅为视觉近似，不等同实际 wx/DPI 结果 |
| 间距 | 延续 4 的尺度：4/8/12/16/24/32；页面边距 24，卡片 20–24，表单组 24、字段间 12；表格用行高和分隔线组织，不给每个字段套卡片 |
| 颜色 | 浅色：背景 `#F4F6F8`、内容 `#FFFFFF`、正文 `#172B36`、次级 `#586B78`、主操作 `#087F83`；深色：背景 `#111A22`、内容 `#19252F`、正文 `#E5EDF2`、次级 `#A3B3BF`、主色 `#50C7C7`。这些是方案 token，实际实现需核对对比度/原生禁用态 |
| 组件 | 控件高 34–36 DIP，行高约 44–48 DIP；按钮圆角 6–8、内容面 12–14、流向区 18；减少外框与卡片嵌套，用留白、浅底色和很轻的阴影分组，表单保留清晰边界。主按钮一场景一个，页内导航/查看为次级按钮 |
| 图标 | 统一 16/20/24 DIP 线条层级，保留文字标签；状态不只依赖红绿。深色不用整张图片硬反色，优先已有单色 SVG/BitmapBundle |
| 表单 | 标签置顶或对齐，必填和验证就近；默认项留主区域，技术项按用途折叠；只读字段与禁用字段可区分且能复制必要内容；保留现有用户明确指定的凭据显示/保存规则，不顺手改变 |
| 列表 | 常用信息固定首列；名称过长省略但可查看完整值；选择以 ID 追踪，不以行号追踪；没有记录、未开启、读取失败分别显示 |
| 反馈 | 就近保存反馈；长任务显示阶段/已用时间和真实可取消边界；无可观测总量时不用虚假百分比；短暂提示不承载唯一恢复入口 |
| 动效 | 导航入场约 220ms、按钮/悬停约 180ms；运行状态用紧凑行、居中 Hub 与弧线颗粒流。只有进行中请求流动；终态、失败、空数据与过期快照停止，可全局暂停并遵循系统减少动态效果。动画不替代文字、证据时间或成功判定 |
| 弹窗 | 常规编辑优先页内编辑；确认仅摘要对象/变化/影响/备份，技术路径折叠；正文可滚、底部按钮固定；Esc 不触发保存，Enter 只触发当前安全默认按钮；关闭后恢复焦点 |

窗口按**可用客户区/DIP**分级：宽度 ≥1180 为列表+详情；900–1179 缩侧栏至约 176、辅助区转下方；720–899 保留文字侧栏约 152，主从编辑改成整页；更窄采用客户端下拉/抽屉导航与单列。高度 ≤640 时去掉非必要概述，仍保留标题和主操作。表单只纵滚，日志技术表允许内部横滚，整窗不横滚。建议目标最小客户区约 720×480 DIP，是否下调当前 900×560 最小窗口必须经过原生验证，不能只改常量。

首批验证目标：1366×768 @100/125%、1920×1080 @100/125/150/200%、2560×1440 @150%；同时覆盖非最大化 1180×760、900×600 和小客户区。屏幕像素、工作区、装饰边框、任务栏和 DIP 分开计算；尤其 1366×768 @150% 下不强行塞两列。macOS 覆盖 Retina 与系统菜单/字体差异。原型窗口检查只能验证 CSS 断点，不能替代 Windows 缩放、跨屏、输入法或 macOS 原生验收。

键盘路径：Tab 顺序与视觉顺序相同，侧栏方向键/Enter、列表选择、编辑保存/取消、弹窗焦点圈闭均需定义；屏幕阅读器读到名称、角色和状态，自绘导航必须附可访问性语义。焦点环与高对比度不能因美化被移除；避免无文字的纯图标侧栏。

## 8. 技术路线与迁移取舍〔基于代码的建议〕

| 路线 | 能获得的效果 | 本项目具体成本与集成 | 推荐 |
| --- | --- | --- | --- |
| 继续 wxDragon 原生 | 新侧栏/页面工作区、主从列表、固定操作栏、统一状态/表单/弹窗、浅深色 | 已有 SimpleBook、SplitterWindow、Sizer、ScrolledWindow、DataView、StyledTextCtrl、PaintDC、Accessible；需要组装公共组件、断点布局、焦点语义和必要 DPI 窄绑定。沿用托盘、系统结束会话、URL/单实例、后台 ownership 与 MSI/App 流程 | **先选这一条**，以状态概览与 WorkBuddy 模型编辑样板证明效果，Codex 接入设置检查能力可达性 |
| wxDragon 局部 WebView | 天才小分队可复用站点原有登录、组织和交易视图；本地其他复杂布局可另评估 | vendor 有可选 wrapper，当前 Cargo 未启用；需新增站点 Hub 布局，验证会话/退出、导航/新窗口、WebView2/WebKit、OAuth/支付返回及两平台打包。不能向网页开放通用本机管理 API | **站点模块推荐先做承载样件**；本地客户端和服务仍优先原生，不据此迁移整个 Hub；详见 [成本与阶段](tiancai-squad-account.md#原生承载与分阶段实施建议) |
| Tauri 等替换桌面壳 | Web UI 迭代空间，Rust 业务可保留 | 新增前端工程、IPC/进程管理、托盘/结束会话/深链/单实例/系统存储适配；现有 native 修复和后台生命周期仍需 Rust 保留。Windows runtime、MSI UpgradeCode/四段版本规则、macOS universal/App/DMG/签名流程都要重新接合，绝不是只重写页面 | 本轮不选；不为设计稿提前引入迁移工程 |

代码能力依据：[SimpleBook](../../vendor/wxdragon/rust/wxdragon/src/widgets/simplebook.rs)、[SplitterWindow](../../vendor/wxdragon/rust/wxdragon/src/widgets/splitter_window.rs)、[Window/accessibility](../../vendor/wxdragon/rust/wxdragon/src/window.rs)、[BitmapBundle](../../vendor/wxdragon/rust/wxdragon/src/bitmap_bundle.rs)、[WebView feature](../../vendor/wxdragon/rust/wxdragon/Cargo.toml)。没有在当前 Window Rust trait 中发现通用 `from_dip/to_dip` 包装；只确认 DC/BitmapBundle 的部分 DPI 能力，必要时补窄 ABI 并同时维护 C++/头文件/Rust，不假定所有尺寸已自动正确缩放。

外部技术参考于 2026-11-07 查阅：Tauri 的 Windows 界面依赖 WebView2、桌面 macOS 开发依赖 Xcode 工具，见 [官方先决条件](https://v2.tauri.app/start/prerequisites/)；其 Core/WebView 进程拆分见 [官方进程模型](https://v2.tauri.app/concept/process-model/)。据此及本仓库集成量作上述成本判断，**未做迁移 PoC、没有内存/体积/工期实测**。wxSimplebook 的能力以已读取本地 vendor 为准。

若原生样板无法满足目标，再按同一模型编辑页对比 WebView：先仅合成数据 → 只读脱敏状态 → 经 Rust 命令适配器处理一项已有受保护保存 → 两平台打包/生命周期验证 → 决定逐页迁移。保留旧壳到新壳覆盖矩阵通过，不同时让两套页面写同一目标。完整换壳必须单独授权实施，不借本次原型默认进入。

## 9. 实施层次、接口与回归〔设计建议〕

建议分四层：`NavigationTarget`（页面/客户端/条目/子页）→ 页面 ViewModel（快照、草稿、证据和错误）→ 任务 Controller（顺序、忙状态、取消/代次）→ 原 ApiClient/后台领域接口。推荐以 `SimpleBook` 容纳页面，侧栏只发导航意图；页面创建函数的父节点从具体 `Notebook` 解耦为普通 `WxWidget`。这不是把旧 Notebook 隐藏后继续散落数字索引。

`enter/leave/resume` 负责只读加载与日志计时器；`GuiMessage`/后台结果继续在 GUI 线程应用。原 `GuiTimers` 托盘暂停、动态 MCP 页面、dashboard 缓存与自动恢复都进入有类型的生命周期，销毁前释放回调和计时器。保持现有日志 5 秒、dashboard 10 秒的基础策略，先不把 CSS 演示速度当作刷新指标。

## 多客户端与当前活动路由（合成规划）

按用户提供的 Magpie 路由截图，把运行状态改为“多客户端纵列 → Hub → 使用中的模型 → 使用中的渠道”。所有当前活动端同时可见，取消逐端切换与重复矩阵；点选行只高亮对应连接并打开就近详情，不筛走其他端。ChatGPT 的 App / VS Code / CLI 执行状态收进本端行，接入设置保留在详情及原客户端页。

用户进一步确认：仅显示已打开或确实在使用接入的客户端；保存了配置但已关闭且没有活动请求的客户端不占运行图。模型只在请求进行中出现，完成、失败、取消、断开或未完整结束后移出图，记录仍留在原请求日志。客户端打开但空闲时保留客户端及 Hub，不保留历史模型；没有客户端打开或在用时，运行图只保留居中的 Hub。读取失败不能把旧快照当作当前活动，退回 Hub 状态未知并提供重新读取。配置、完整模型列表及低频维护继续从管理页进入。

默认合成快照为三个已打开客户端、一条 WorkBuddy 进行中模型路由；“全部客户端已关闭”可直接核对只剩 Hub。“8 个客户端同时打开”是显式容量演示，额外 A–E 是规划占位，默认不显示，也不代表产品新增适配。演示选择收在小型展开区，不占首屏主信息。

品牌图标保持原色，用小状态点和短标签表达运行/配置证据；Hub 只表示本机服务。已打开与配置正确不等于上游可用。普通入口仅在有进行中请求时出现，客户端归属保持未知；Codex 进程打开的合成观察单独提供，不从 App/VS Code/CLI 执行连接或普通模型请求反推。模型、来源、入口与条目身份共同确定路由；不同专用端的同名模型不合并配置。同一路由并发请求可合并显示数量，完整请求身份继续保留。

仅进行中请求沿对应路径流动；终态、空闲、未知快照和 Hub 不可用停止。Hub 恢复后等待新证据，旧进行中快照不恢复流动。全局暂停及系统减少动态效果继续生效。全局图的聊天、Skill、MCP 和 Dumpling 保留紧凑摘要；客户端页改为六节点概览图，聊天/执行/天工桌面同步详情仍可查看；配置差异、失败记录和检查来源有定向入口。失败只说明该请求结果，不猜具体故障节点。

以上均为原型设计，不扩大当前产品检测能力：天工已有运行检测及当前运行的本机请求证据，WorkBuddy 现有概览主要是配置状态，Codex 执行通道与模型请求归属仍分开。原生实施须逐端补齐可观测字段和可信的新鲜度，缺字段不能当作未启动，也不能伪造成功。

左侧默认三端依次为 ChatGPT(Codex)、WorkBuddy、天工 Work；访问或成功配置已在这三个位置中的客户端时不重排，只更新使用记录。列表外端进入时替换最久未使用的那个位置，其余位置不动。收起时“⋯”在第三端下方；展开后该按钮隐藏，“客户端”标题右侧显示“收起”。原型仅用合成内存，正式版需用 Hub 自己的记录，不以资源网格排序改动导航。

全局资源保留使用端摘要，打开后用紧凑图标网格；客户端选择采用每行 2–4 个的紧凑图标网格：图标在上、名称在下，单块最大宽 124 CSS px、最小高 84 px，图标容器 26 px；不再横向撑满弹窗。点击已有资源的目标后，配置成功才点亮；使用中的排在前面，组内保持原目录顺序；再点并成功停用后变暗。失败不改旧选择和顺序，读取失败保留上次选择并禁用修改。这个排序只用于资源选择网格，不重排左栏。新增表单的勾选只是目标草稿，一次“添加并使用”成功后才成为实际使用。 Magpie 的 74 名只用于研究，首批按用户指定学习 Cursor、VS Code、DeepSeek Harness、ZCode、WorkBuddy，不把研究名单当新增支持。

原型不再以一条假定矩阵禁用天工：既有 Dumpling 三端适配保留；通用远程 HTTP MCP 可演示规划，天工 Skill/本地命令格式待核实并提供原因。Dumpling 补齐环境编辑、密码与应用/浏览器字段及条件高级项，先保存环境再授权/连接；新建环境不再切换全局首次接入场景。默认客户端页显示已有配置及使用数量，显式首次接入才显示空态，未知、待授权和未使用仍区分。

MCP 添加默认完整“表单配置”，并列可编辑“JSON 配置”；名称、可选简介、连接类型、HTTP 地址/认证/Headers，或 STDIO 命令/逐行参数/环境变量/传递变量/工作目录均直接可见。两视图共享草稿，JSON 多服务先明确选一项，错误保留原文；客户端选择与一次“添加并使用”同窗，已有配置沿原身份复用。取消前两轮用途分类和单粘贴框首屏，不隐藏基本字段。Dumpling 仍走环境与原授权。统一下拉保留展开、搜索、键盘/焦点与深色规则；正式 Rust 复用字段模型和领域编排，HTML/CSS 不直接成为 wxDragon 控件，完整兼容合同见 [管理规格](desktop-capability-management.md)。
