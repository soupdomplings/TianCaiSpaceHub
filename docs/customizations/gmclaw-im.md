## 范围

Hub 复用已有飞书、微信、企业微信账号的接收与回复通道。`/tg` 切换当前发送者到天工 Claw，`/gpt` 返回 ChatGPT（Codex）原有执行流程；旧 `/gmclaw` 入口继续兼容。`/wb` 是明确标注暂不支持的保留入口，提示后保持原执行端与会话，不把消息转发给 WorkBuddy、Codex 或其他替代执行器。WorkBuddy 现有模型配置仍独立工作，边界见 [WorkBuddy](../workbuddy.md#外部消息执行端边界)。

天工拥有独立会话和工具审批，不接管 Codex remote-control 连接，也不把天工会话冒充 Codex 线程。`/s` 沿用停止语义，`/q` 沿用退出当前会话语义；具体可执行的操作由当前执行端能力决定。

天工的新建、恢复、目录选择和模型选择进入现有平台会话流程：飞书使用原会话卡片与表单，微信使用原文字菜单，企业微信继续通过 `TextChatAdapter` 使用同一流程及其原有卡片。底层由 `session_backend` 选择 Codex 或天工数据与操作，不再维护天工专用的 `projects.rs` 菜单。审批也复用平台原有布局和按钮或文字选项，但采用独立天工待审批与回调执行路径，不提交到 Codex。天工普通任务支持文字、最终答复、当前轮工具批准/拒绝，以及下文按平台能力更新/收尾的临时准备回复状态；附件、逐字进度、通用工具进度卡片和主动取消未因此新增。Telegram 沿用原流程，不接天工。第二阶段不包含 MCP 连接的新增、修改、删除或启停；天工已安装的工具仍由 Harness 执行。

## 直接从聊天接入

Hub「天工 Claw 接入」页提供模型配置、「启动天工 Claw」按钮与简短使用指引，不提供「IM 桥接」配置框，也不要求用户预先填写地址、Token、项目目录、执行模型 ID 或最大步数。

1. 按 Hub 原流程配置并连接飞书、微信或企业微信账号。在已连接的聊天中，由允许的发送者发送 `/tg`。
2. 首次点击「启动天工 Claw」，或先手动打开天工再发送 `/tg`；已有实例仍可直接接入并保存 IM 对话。要让已打开窗口同步外部消息，首次请正常退出原手动实例，再通过 Hub 启动按钮打开一次以启用桌面同步。Hub 核对原有权限和任务保护，自动准备连接并识别同用户运行授权；只有显式连接/启动时桌面未运行且端口可用才启动，已有实例直接复用、不自动重启。启用后后台恢复连接，不必再次 `/tg` 授权；`/tg` 仍用于选择执行端。
3. 点击或选择原平台的“新建会话”，或发送 `/tg new` 直接进入同一新建设置界面。选择项目目录、模型，再通过该平台已有的创建按钮或文字确认创建会话。
4. 发送 `/q` 退出当前会话，选择其他项目的新会话或恢复历史；发送 `/gpt` 返回 ChatGPT（Codex）。

只有显式「启动天工 Claw」、`/tg` 或 `/tg new`（以及对应旧命令）准备连接配置、按需启动天工。按钮调用 `POST /api/gmclaw/runtime/start`，先取得最新 Hub 配置版本，再由服务端核对 `expectedRevision`、启用连接并仅在口令为空时生成内置口令，保存后在实际启动前和结果返回时再次核对配置。与 IM 共用启动互斥、进程/端口核对和最多 30 秒的就绪等待；GUI 请求最多 45 秒。未就绪时如实提示等待或失败，不把“已发起启动”当成“已连接”。按钮不需要预先创建模型数据库，不创建项目/会话，不发送模型或工具任务，也不改变任何 IM 发送者的执行端或会话。

`gmclawBridge.enabled=true` 后，Hub 本地服务启动即开始后台连接检查，每 5 秒检查一次；单次检查耗时较长时后续周期顺延。普通任务前的检查也可自动恢复运行授权，概览优先使用最近的同配置观察结果。自动恢复不启用尚未启用的接入、不启动或关闭桌面、不重放任务。Hub 保存的启动口令仅在原值为空时生成，已有值复用；只向其新启动的天工子进程注入 `GMCLAW_AUTH_TOKEN`，不修改系统环境变量或安装资源。点击按钮后即使安装缺失或连接失败，已成功保存的启用/口令配置仍保留；回退或停用时按下方维护说明核对。

天工 1.1.1 手动启动会生成新的随机口令，不等同于 Hub 保存的启动口令。本轮先使用内存缓存和保存口令核验；不匹配时，已启用接入的后台、普通检查或显式连接会自动核对官方完整安装、当前操作系统用户、桌面与内置 Python 的父子关系、启动身份、Harness 脚本及固定参数，再仅取得该 Harness 的临时授权。Windows 使用隐藏的系统 PowerShell 查询，macOS 使用进程元数据和参数边界；发现最多等待 8 秒，多匹配或不能核验时拒绝连接。同配置并发状态检查共享一个最多 18 秒的探测任务，概览短超时不会反复终止授权发现；失败的发现按配置至少间隔 5 秒。临时口令只在内存中用于本机授权请求，不写 Hub 配置或会话关联文件、不显示到 IM/概览或日志。授权发现不读取模型密钥或会话正文。正常手动打开的实例无需退出；识别失败时提示核对同一系统用户和服务状态，已启用的接入继续自动检查，不要求每次重启重新授权。

天工安装默认自动查找。Windows 优先使用 App Paths 和卸载注册表（当前用户/本机、32/64 位视图），兼容 `InstallLocation`，并从 `DisplayIcon` 或 `UninstallString` 所在目录查找 `tiangong-desktop.exe`；官方安装可只登记 `.ico` 图标且没有安装目录，不再把图标当作主程序。路径只解析不执行注册表命令，支持非 C 盘，常见目录作为后备。实际启动仍核对正式 EXE 名、`app.asar` 和配套 Harness；macOS 使用完整 App。旧自定义路径/地址保留；自动启动要求默认 `http://127.0.0.1:7861`（`localhost` 归一），不会尝试更改天工端口。

授权与组件连接检查只访问本机 `GET /health` 和 `GET /ctrl/status`：健康响应必须符合约定，未带授权的状态请求应被拒绝，带已核验口令的状态请求应返回运行中且组件全部就绪。缺少授权保护、口令不匹配、组件未就绪、异常或超时都不会标记已连接。单次 HTTP 最多 2 秒，连接建立最多 1 秒，完整检查最多 18 秒，避免原 6 秒外层预算截断串行健康与授权检查。响应限制 32 KiB，不公开组件原始消息或口令。后台连接检查不创建会话、不提交 `POST /v2/chat`；新建、恢复与执行才访问下方桌面任务接口。

`/tg` 为退出过渡和初始化最多等待 30 秒，仅重复只读状态检查，不重试模型/工具执行。连接超时与已建立连接后的响应超时分别处理；没有桌面进程时还会核对固定端口可用，再启动一次。运行中、端口仍被占用或最近启动尚未确认时不重复启动、不强杀；启动后立即释放配置锁再等待。等待结束仍未就绪时明确提示初始化或检查原因，只有授权和组件核验通过才报告已连接。

### Hub 退出与端口释放

本轮针对 Windows 上“天工保持运行，退出 Hub 后 `3847` 仍被占用”的反馈修复启动链。静态核对发现原 Windows 监听套接字可能被天工子进程继承；只结束 Hub 不能撤销已经继承到其他进程的句柄。新的主监听与 IPv4/IPv6 兼容监听经 `bind_service_listener` 创建不可继承的系统监听，再明确清除继承标志，失败则关闭并报告错误。Windows 启动天工改用 `CreateProcessW(bInheritHandles=FALSE)`，继续传递同一正式程序、固定本机同步参数、工作目录和仅子进程的授权环境；不修改系统环境或安装资源。

正常退出 Hub 先请求后台关闭，最多等待约 1.5 秒，必要时只结束 Hub 自己拥有的后台进程；启动恢复的最后终止手段同样不再使用整棵子进程树。天工桌面与已有任务保持独立，不因关闭 Hub 被结束；也不强制结束其他程序占用的端口。非 Windows 监听行为沿用原实现，macOS 实机退出/重开仍待验收。

这项修复防止新启动链的继承，无法替旧天工实例关闭它已持有的套接字。升级时如仍遇到旧实例占用端口，用户应先到天工核对任务和审批，再按天工正常方式退出该旧实例一次，换新 Hub 后重新启动天工。此一次迁移只针对旧句柄，不要求后续退出 Hub 前都关闭天工，也不改变先前作用域修复无需重启天工的历史结论。回退旧程序后继承问题可能再次出现；本轮没有重置配置或删除会话，关闭/替换程序不表示任务取消。关键代码见 [服务监听](../../src/main.rs)、[Windows 天工启动](../../src/gmclaw_runtime/windows_start.rs) 和 [Hub 后台退出](../../src/gui/daemon.rs)。

### 在 IM 中选择项目目录

天工与 Codex 共用同一平台的“新建/恢复 → 会话设置 → 创建”流程、目录输入与分页规则；不再提供上一阶段天工独有的 `/0` 目录菜单或额外 `/y` 目录确认步骤。按界面当前显示的按钮或序号操作，微信仍可使用共同设置菜单的 `y` 创建、`n` 取消。飞书使用原卡片表单及自定义目录输入，企业微信保持原卡片能力和目录输入流程，不要求所有平台显示完全相同的控件。

- 新建设置的目录候选依次合并 Hub 默认目录、天工官方全部场景的有效 `work_dir`、当前发送者在当前聊天中且连接指纹相同的当前/已退出会话目录；不读取 Codex 项目列表。手动创建的项目即使没有任何任务，也能成为候选，不再从任务列表反推全部项目。目录按上述顺序去重，Windows 统一大小写、正反斜杠、尾分隔符、`.` 及系统路径前缀，macOS 保留大小写差异。官方默认场景空目录映射到天工真实用户数据目录的 `workspace`；非默认场景空目录没有可选择路径，不能凭空补造。
- 项目目录只读官方 `GET /data/scenarios` 的 `scenario_id/work_dir`；响应仍可带任务摘要，Hub 项目 DTO 不解析会话正文，也不读取私有数据库/日志。单次响应最多 8 MiB、场景和合并后的唯一目录最多各 20000 项，字段缺失、重复场景 ID、非法非空目录或超限都明确报告未完整读取，不静默截取。项目连接、读取及前后作用域/配置/运行身份核对最多 20 秒，模型读取并行最多 5 秒，汇总后另以最多 5 秒复核实例。项目读取失败时保留本地默认及当前发送者已有目录，设置页说明范围不完整、可自定义或重新进入重试；权限、菜单或配置已失效时不提供旧候选。浏览不创建目录、场景或任务，最终创建仍走原流程，并以同一路径身份规则复用已有场景。
- 默认目录优先使用格式合法的旧 `projectPath`；没有该值时使用天工模型数据库所在目录下的 `workspace`，与天工桌面默认目录结构一致。默认路径通常为 Windows `%APPDATA%/tiangong-desktop/workspace`、macOS `~/Library/Application Support/tiangong-desktop/workspace`；设置 `GMCLAW_CONFIG_PATH` 时跟随数据库所在目录。合法旧路径可以尚不存在，不要求先建文件夹。
- 自定义目录应是运行 Hub 的电脑上的绝对路径，支持展开 `~`。天工侧限制为最多 4096 字节、不含控制字符。微信/企业微信在目录输入状态优先识别本机绝对路径，因此 macOS `/Users/...`（包括空格）不会因 `/` 开头误作普通命令；已知控制命令继续生效。
- 浏览目录、修改草稿、读取模型列表不创建目录或调用模型。只有共同流程最终的“创建会话”动作才创建缺失目录并规范化路径；天工目录处理最多等待 10 秒。失败或超时不会绑定新会话，也不删除已经创建的目录；底层文件操作可能仍在完成，回复会提示检查后重试。
- 创建目录前后重新核对权限、当前执行端、连接指纹及会话请求；创建目录后还需登记天工桌面任务与会话，最后再次检查权限和菜单请求才绑定。恢复时核对桌面原目录确实存在且为文件夹，不自动改用其他目录或创建替代目录。创建/恢复错误通过共有流程回显，未确认的桌面写入不自动重试。
- 每个天工会话固定自己的规范化目录；后续文字、工具审批和历史恢复沿用它，不随其他会话、默认目录或旧 `projectPath` 的修改而漂移。历史列表由同一平台 renderer 展示目录信息，未知状态条目仍不能恢复。

会话目录和发送者身份隔离不等于文件系统沙箱。天工工具策略可能直接执行目录中的部分读写或低风险操作；不能依赖 IM 审批逐次拦截所有工具。

飞书目录下拉按每页 20 个真实目录显示，默认/自定义项常驻；已选目录位于其他页时补入当前页并保留选择。翻页保留自定义路径、模型、推理与权限草稿，最终提交缺失的字段沿用已保存草稿，显式清空自定义输入不会恢复旧值。企业微信目录下拉最多 10 项，包含默认、自定义及当前已选真实目录；其余目录保留在完整列表，卡片提示回复共同设置菜单的 `1` 或 `/1`，使用既有每页 8 项文字分页。微信沿用相同的 8 项文字分页。这里扩展平台共有会话设置，不另造天工目录规则；飞书翻页动作携带来源页并核对当前草稿页，旧页动作、缺失或非 object 表单拒绝；下拉使用实际 option 的 `initial_index`，自定义输入使用 `default_value`，避免把仅展示内容的 `initial_option` 当成选择 value。读取候选后再核对菜单作用域、允许名单和连接配置，失效数据不用于呈现或创建。真实分页与表单保持待用户验收。

### 在同一表单中选择模型

模型列表只读天工既有 `model_configs` 中的 `model_id`、`model_name`、`is_active`，同时包含天工原生配置及 Hub 管理条目，不读取或展示 API Key。模型名称用于显示，真正选择的是数据库 `model_id`，相同名称的不同条目仍可区分。读取最多等待 5 秒；读取失败在设置页说明，创建前再次核验，不能凭空生成一个可用模型。

企业微信共用设置卡片的模型下拉最多 10 项（含“使用当前模型”，因此最多展示 9 个真实模型）。模型更多时，卡片提示发送共用菜单的模型序号（当前为 `2` 或 `/2`），进入原有每页 8 项的完整文字列表，并按提示翻页选择。选中超出卡片首批的模型后，该项补入卡片末项，保留默认选项与 10 项上限；选中模型随后被移除时仍保留所选 ID 供后端明确拒绝，不静默改成默认。这是企业微信共有卡片的修复，没有增加天工专用菜单；真实卡片与分页行为待用户验收。

选择“使用当前模型”时，在创建时依次解析旧 `gmclawBridge.modelId`、天工当前默认模型；显式表单选择优先。没有可用默认或选中 ID 已不存在时拒绝创建并要求重新选择。创建成功后把实际 `model_id` 固定在会话中，任务、审批与恢复继续用同一 ID；以后切换天工默认模型不会改变已有会话。Hub 不复制该条目的完整参数，后续对该模型条目本身的修改仍由天工/模型网关处理。

Hub 创建的会话把实际模型 ID 保存在独立会话关联文件，重启后恢复仍使用同一 ID。恢复桌面原生会话时，优先使用已有 Hub 关联；没有关联则按天工会话元数据中的 `model_name` 唯一匹配当前模型配置。非空历史缺少模型记录或同名模型不唯一时拒绝恢复，不改用默认模型；只有没有消息且没有模型记录的空会话，才可使用天工当前默认模型。恢复会话及每次提交任务前，Hub 都再次只读核对固定模型 ID 是否仍在天工目录中，读取最多等待 5 秒。模型被移除或目录读取失败时，不提交任务、不切换到默认模型，保留原会话与待审批；需恢复对应模型或重新选择模型创建会话。这样避免天工收到未知 `model_id` 后静默回退默认模型，不能把默认模型存在视为原会话模型仍可用。

共同 `ThreadCreateDefaults.capabilities` 表明天工不支持在此会话表单覆盖推理强度或 Codex 权限模式，因此共用 renderer 和文字菜单隐藏这些选项，并显示继承说明：思考参数沿用所选模型接入配置，工具权限沿用天工策略。提交不支持的非默认值也会被校验拒绝，不将隐藏控件理解为已经应用 Codex 沙箱。Codex 默认能力与原菜单顺序保留；菜单显示和数字解析使用同一动作表。
### 配置兼容与维护

天工执行请求使用 `POST /v2/chat` 和 `Authorization: Bearer ...`。地址只接受本机回环 HTTP/HTTPS 根地址或 `/v2/chat`；禁止账号、查询参数和片段，不经过系统代理、不跟随重定向。模型保存无需重启的用户反馈属于 [模型配置](gmclaw.md#使用与多模型管理)，不证明 IM 授权、任务或工具执行已验收。

Hub 继续将连接设置保存在自身 TOML，用于兼容和后台维护，不重新暴露 GUI 桥接表单。以下仅为默认未准备状态示例：

```toml
[gmclawBridge]
enabled = false
endpoint = "http://127.0.0.1:7861"
authToken = "" # 显式 /tg 时自动准备；勿将真实值写入文档
projectPath = "" # 合法旧值可作默认目录；创建后使用会话自己的目录
maxSteps = 30
# desktopPath = "<天工完整安装的绝对路径；省略时自动查找>"
# modelId = "tiancaispacehub-<entryId>"
```

| 字段 | 默认与兼容行为 |
| --- | --- |
| `enabled` | 默认 `false`；显式启动按钮或 `/tg` 自动准备时启用。启用后后台及任务前检查可自动恢复运行授权，普通消息不自行启用或启动桌面 |
| `endpoint` | 默认 `http://127.0.0.1:7861`；仅本机回环地址，旧自定义值保留 |
| `authToken` | 默认空；显式连接准备时仅空值自动生成，旧值复用，用于 Hub 主动启动天工；手动实例临时授权不覆盖此值。启用后要求非空 ASCII、无控制字符、最多 8192 字节 |
| `desktopPath` | 默认省略；兼容已有完整安装路径，留空自动查找 |
| `projectPath` | 默认空；合法旧值作新会话默认目录，否则使用数据库同级 `workspace`；不是启用必填项、不加入连接指纹，不覆盖已建会话目录 |
| `modelId` | 默认省略；新会话未显式选模型时优先兼容此 ID，否则取天工当前默认模型；实际 ID 创建时固定到会话，最多 256 字节、无控制字符 |
| `maxSteps` | 新建会话默认 `30`，允许 `1–200`，保留旧配置；恢复原生历史按下文单独兼容 `1–1000` |

显式连接准备仍使用配置版本与原有保存保护，避免覆盖并发模型配置。保存连接设置不代表连接成功；真实启动前需要重新核对配置，发生冲突时提示重试。概览每 10 秒刷新，客户端摘要检查限时 1.8 秒；天工授权概览优先复用同配置最多 15 秒的最近观察，没有结果时显示自动检查中。后台探测与前台共享探测任务，任务提交前仍重新核验连接，不凭概览缓存执行。后台和概览不生成持久口令、不保存配置或启动程序。

## 按接入页签显示概览

状态概览随「Codex 接入」「WorkBuddy 接入」「天工 Claw 接入」切换；初始显示 Codex，大模型、聊天工具与日志等公共页签保留最近接入端的视角。切页只是本机显示，不向 IM 发送切换命令，不改变任何发送者的实际执行端或会话。

- Codex 显示桌面、VS Code 插件和 CLI 的原有控制通道状态。
- 天工分别显示模型接入与外部消息授权状态。模型接入核对天工进程、已保存条目是否指向当前 Hub 的回环地址/端口和专用路由，以及当前 Hub 运行内收到的对应条目请求；满足条件时显示绿色“已连接”，不把厂商模型调用结果当作本地连接的门槛。模型验证由用户在天工中完成；概览不主动调用模型。尚未启动显示已保存但未启动，已经启动且尚无本地请求显示“等待连接”；地址与当前 Hub 不一致时提示重新保存。外部消息未准备时仍显示“待首次使用”，提示在 IM 发送 `/tg` 自动连接，授权/组件检查通过才显示外部消息连通；Telegram 标明不支持天工。
- WorkBuddy 显示独立模型配置状态，外部任务及 IM 线路继续标明暂不支持；`/wb` 仍不会切换。
- 飞书、微信和企业微信的通道状态与执行端状态分开；通道已接入但天工未连通时会提示原因。模型到 Hub 的连线依本地模型请求证据独立显示；IM 到天工的连线仍要求执行端与对应消息通道都就绪，不能把保存模型或模型本地连接解释为 IM 整条链路打通。

2026-10-06 上一阶段的未发布概览修复仅在成功解析并路由到天工专用渠道的请求中，识别 Hub 生成配置使用的本地客户端标识，记录专用条目与 Hub 监听地址对应的活动；失败的厂商请求也证明该本地连接已到达 Hub，关闭请求日志不影响此判断。证据只保存在当前 Hub 进程内，不读历史日志推导当前连接，也不记录口令或请求载荷。天工进程停止或进程身份变化、Hub 监听地址变化，或对应条目删除、停用、改为其他地址后，旧证据失效；重启后的天工/Hub 需重新观察到本地请求才恢复绿色。仅调整该条目的上游厂商或调用参数，不影响同一专用入口的本地连接证据。此前保存配置就绪及 Harness 授权均不能替代模型 API 的本地连接证据。新增状态字段向旧概览响应兼容，缺失字段保持未连接；未改变用户配置、模型路由或调用成功的定义。该阶段的 Windows 编译不替代本轮自动恢复与桌面任务修复验证；未执行真实请求，最终产物及本轮编译见品牌专题。

`GET /api/gui/dashboard` 新增 `clientOverview` 脱敏摘要，仅包含模型存在/数量/配置状态及桥接启用/连接状态；不返回口令或完整客户端配置。状态读取限时，旧服务不返回新字段时显示读取中，不把未知状态当作连接成功。

## 指令、会话和权限

| 指令或入口 | 行为 |
| --- | --- |
| `/tg` | 自动准备连接并切换到天工；已有会话保留，没有会话时打开该平台共有的新建/恢复入口 |
| `/gpt`、`/tg off` | 返回 ChatGPT（Codex）原流程，保留天工自己的会话记录 |
| `/wb` | 提示暂不支持外部任务，保持原执行端与会话 |
| `/q` | 退出当前天工会话并重新打开共有会话入口；保留天工模式，不表示停止任务 |
| `/tg new` | 通过运行/审批保护并自动准备连接后，直接进入共有新建设置 |
| 平台原有新建、恢复、目录、模型与翻页控件 | 继续使用同一平台的卡片动作或文字规则；序号以当前显示的菜单为准 |
| `/s` | 提示当前接口不支持远程中断，需在天工桌面停止，不伪造成功 |
| `/tg status`、`/tg help` | 查看当前执行端、会话状态或帮助 |
| `/tg approve <确认码>`、`/tg reject <确认码>` | 兼容及卡片投递失败备用；仅批准/拒绝当前会话最近一轮完整列出的工具，正常按平台按钮或 `/1`/`/2` 操作 |
| `/gmclaw` | 兼容旧天工入口及 `new/status/help/off/approve/reject` 子命令 |

`/q` 和 `/gpt` 不等价：前者仍在天工模式内选择会话，后者改变执行端。回到 Codex 后，原有 `/s`、`/q`、会话选择和执行继续由 Codex 处理。天工会话设置和列表只使用天工数据，不会为了显示同样的界面而创建或调用 Codex 线程。

IM 绑定身份仍包括平台、Hub 账号、聊天 ID 和发送者 ID，群聊不同发送者各自选择会话与操作自己的卡片。底层执行改为真实天工桌面身份：新建会话使用桌面原生 `user_id=local`、真实 `session_id` 和项目身份；恢复则沿用桌面元数据中的原身份与项目。默认项目的记忆身份为 `0`，其他项目使用真实 `scenario_id`。这样才能继续原生会话记忆，不能再以 IM 发送者哈希创建一个桌面看不到的平行会话。任何获准发送者可选择全部桌面任务，列表范围已按用户要求扩大；它不等同于原先按发送者划分的私有历史。不同发送者仍以同一个本机进程权限执行，未建立文件系统沙箱。审批码只能由对应发送者在对应聊天使用，但群内回复的可见性仍由平台决定。

进入天工前继续使用原 IM 账号允许名单和飞书群提及规则；允许名单为空延续原平台“允许所有”的语义。自动连接、创建/恢复、等待执行槽后和发送结果前分别按当前配置复核。原 Codex 处于启动、执行或待审批时不能切入天工；天工执行/排队期间不能切换或换会话，有效待审批必须先处理。切换和关闭连接均不表示任务已经停止。

共有会话界面的隔离通过 Hub 内部 `session_scope` 完成：作用域包含平台、账号、聊天、发送者、连接指纹、绑定随机值和界面代次 `ui_epoch`。`session_scope`、`session_entry` 使用 `#[serde(skip)]`，外部传输 JSON 无法提供这两个内部字段。进入新菜单、成功创建/恢复或切离执行端会更新代次；已有会话的旧卡片、其他发送者卡片、旧 Codex 卡片及配置变化前的回调必须通过当前作用域校验才允许使用。恢复回调的目标任务必须已显示在当前请求的列表中，再通过桌面接口核对真实任务与会话对应关系；不能直接传一个任意 ID。

请求 ID 使用 `thread-route-<随机 UUID>-<递增序号>`，避免 Hub 重启后重新使用相同的卡片请求编号；列表排序仍以最后的序号为准。普通非空消息 ID 按发送者身份在内存保留最近 512 条去重。一个卡片的不同操作可能共用消息 ID，因此卡片动作不按这份文字去重表丢弃，改由请求 ID、作用域与当前阶段校验约束。天工作用域内的共有会话界面不会改写 Codex 的 `last_route`，也不会落入其模型请求或审批提交路径。

同一平台、账号、聊天的分派入口串行检查执行端选择与任务准入，不承诺网络时间严格排序。天工开始排队执行前释放聊天分派锁，同一发送者继续由自己的会话锁保护；其他发送者不被整轮任务阻塞。天工按发送者隔离，Codex 原有绑定仍按聊天维护。

执行端选择、发送者绑定、活动占用与审批确认码仍只保存在 Hub 内存：最多 128 个发送者绑定，每个绑定最多最近 32 条已退出记录；`/gpt` 保留该绑定，因此不会释放绑定容量。真实任务、消息和会话元数据由天工保存，Hub 另持久保存必要关联及未确认标志。Hub 重启不自动恢复 IM 执行端选择、当前绑定、菜单或工具确认码；允许的发送者进入天工模式后可重新读取桌面历史，不能因此自动续执行未确认任务。活动占用按真实 `session_id` 分配，同一 Hub 内一个会话不能同时绑定给不同 IM 发送者；`/q` 或允许的新建释放占用。成功 `/gpt` 切离会释放当前会话占用，但保留该发送者内存中的当前会话；再次 `/tg` 返回时必须重新取得占用。如果已被另一发送者使用，会提示未恢复该会话，可用 `/tg new` 选择其他会话。此占用不控制用户在天工桌面的操作，任务提交前还需核对桌面持久记录与最新轮次事件，不能将它当作原子的实时状态查询。

连接指纹包含 `enabled`、`endpoint`、`authToken`、`modelId` 和 `maxSteps`，不包含 `desktopPath` 或兼容 `projectPath`。连接指纹改变后，旧会话不能继续交给新连接，旧审批不可复用；需先到桌面核对旧任务并显式新建。改变旧默认目录不会移动已经创建的会话目录。

## 桌面任务、对话与历史

原实现只调用 Harness 执行并维护 Hub 内存会话，没有通过天工桌面数据服务登记任务和消息，因此可以在 IM 得到回复，却没有对应的桌面任务。本轮使用天工 1.1.1 已有的、带授权的本机 DataServer `http://127.0.0.1:18768`，与默认 Harness `http://127.0.0.1:7861` 共用已核验运行授权。真实桌面会话只支持该默认官方服务组合；旧自定义回环地址保留在配置中，但不能假设它对应另一套桌面数据服务。

| 官方数据接口 | 本轮用途 |
| --- | --- |
| `GET /data/scenarios` | 读取项目及各项目全部任务，核对真实任务身份 |
| `POST /data/scenarios`、`POST /data/tasks`、`POST /data/sessions` | 登记缺失项目、新任务及原生会话元数据 |
| `GET /data/sessions/<sessionId>`、`GET /data/sessions/<sessionId>/messages` | 核对记忆身份、模型名称及处理/审批状态；不以事件正文补写历史 |
| `GET /data/tasks/<taskId>/messages` | 核对没有模型记录的原生任务是否确实为空，支持接口原有消息分页 |
| `POST /data/tasks/<taskId>/messages`、`PUT /data/tasks/<taskId>/messages/<messageId>` | 写入本轮用户消息、回复占位及后续答复更新 |
| `PUT /data/tasks/<taskId>`、`POST /data/tasks/<taskId>/complete` | 更新本轮标题及正常结束的完成标记，不调用标题生成模型 |

数据请求不经过系统代理、不跟随重定向；单次完整请求最多 5 秒，连接 1 秒、读取空闲 3 秒，创建项目/任务组合操作最多 20 秒。各接口独立验证返回身份、状态与尺寸；消息与列表最多 8 MiB，元数据最多 256 KiB，会话事件最多 4 MiB。自动鉴权恢复只表明 Harness 就绪；桌面数据接口异常仍会阻止创建/恢复或明确提示保存未确认，不将概览绿色视为所有持久化操作成功。

- 最终创建动作按目录匹配已有桌面项目；没有匹配项目时登记 `scenario`，再登记真实 `task` 和 `session` 元数据。Hub 新项目名称和新任务 ID 带 `TianCaiSpaceHub` 来源标识，任务标题初始为“新会话”，首次文字后按内容更新；执行仍沿用同一会话 ID、项目目录与选定模型。创建部分失败时可能已留下项目或空任务，会提示到天工核对，不自动重试、删除或把失败当作未产生任何写入。
- 每轮提交前保存 Hub 未确认标志，再写入桌面用户消息和回复占位。执行中的文字及确认/结束事件更新同一回复消息，结束时写入最终完整答复；桌面消息角色遵循天工的 `user`/`system` 格式。正常结束会尝试标记任务完成；写入或完成标记未确认时如实提示。展示同步不等于向模型重放消息，不扫描日志补会话，也不修改安装资源或直接操作桌面数据库。
- “恢复历史会话”读取桌面所有 `scenario` 下的任务，包含桌面原生任务和 Hub 新建任务，按更新时间排序；共有界面仍按原平台分页，目前飞书、微信、企业微信均为每页 8 条。接口限制项目数及任务总数各为 20000 条、响应 8 MiB，超过范围会提示整理历史；“全部”指该官方任务接口可返回的桌面任务，不包含已删除任务或只有孤立 Harness 记录的会话。
- 恢复先核对当前菜单请求、真实任务身份、原目录、模型及会话状态。有运行事件的会话必须核对最后一轮已经结束且没有未处理确认；不再仅凭持久 `processing` 字段拒绝已结束的会话，具体判定见下节。`running`、`awaiting_confirmation`、无法识别的状态以及 Hub 保存的待审批/未知标志仍阻止普通恢复；不从桌面事件重新生成 IM 审批码。被其他 IM 发送者占用的任务仍可列出，但不能重复绑定。每次执行前再次核对任务未被删除或更换会话、记忆身份未变化及最新事件状态；该只读核对不会锁住天工桌面的操作。

天工 1.1.1 官方没有外部窗口刷新接口，而且已打开任务使用内存缓存；即使重复点同一历史任务，也不会重新读取正文。此前只有持久保存的实现不能让该窗口看到后续 IM 对话。本轮加上下面的局部同步，不通过模型重放、整页重载或自动关闭/重启解决。

成功恢复、用户消息/回复占位保存后和本轮终态保存后，将任务/会话 ID 加入内存刷新队列，最多 128 项。回复来源由独立内存缓存保存，最多 128 个任务/会话键、每键最近 128 个 Hub 回复行 ID；出队、更新成功、任务未打开或同任务被新消息覆盖不会抹掉来源。失败时合并同任务/会话的在途和新排队 ID，不覆盖更新的任务标识；按原生递增行 ID 留住较新来源，避免旧快照挤掉新回复。队列和缓存不存正文或授权。独立后台每 5 秒尝试一项，不拖延原授权检查或 IM 最终回复；单次适配最多 12 秒，外层最多 13 秒。天工 renderer 使用自身临时授权从固定官方 DataServer 读取消息/摘要，同步函数只返回固定结果码；但用于定位 Vue 引用的作用域属性枚举会让原生 primitive（包括已加载的临时授权）短暂进入 Hub 本机内存，不选择或输出运行口令，不写配置、文件、日志或接口。正文和草稿引用不展开预览。常规路径在检查或更新后尝试 `Runtime.releaseObjectGroup` 释放本轮远程句柄；`display` 函数的 12 秒整体限时取消 future 时可能来不及完成显式释放，只会断开本次 CDP 会话，不能把断开记录成释放已确认。

窗口中任务未打开时只刷新原生项目/任务缓存，不切换窗口；已打开时使用局部响应式更新，保留已加载的较早消息、缓存时间和未持久化的展示属性。桌面正在流式执行、等待审批、加载历史或模型、打开/删除任务，有未落盘消息，或消息/项目快照在读取期间变化时暂缓。原生结束后其最终写入可能尚在排队；已有原生行的正文、附件、思考步骤未与持久记录一致时不覆盖。仅准确登记的 Hub 回复行允许后续更新，renderer 中为这些行保留临时来源标记，不回写官方数据。延期保留队列重试，不把展示失败当作执行失败，也不自动重放模型/工具请求。

能力核对同时确认实际写入对象可写：`scenarios`、`messages`、`showWelcome`、`hasOlderMessages` 的 Vue Ref 不能是 readonly，组件实例的 `seedMessages`、`messageSummaries`、`hasOlderMessages` 缓存字段也须允许写入；纯读取的模型、运行/审批等 Ref 不额外要求可写。字段形状、可写能力、任务/会话身份及原生状态在异步消息读取后再次核对，读取期间对象变为只读、缓存写入不允许或原生状态变化时保留原窗口，不把停止页面更新解释为任务执行失败。

首次读取最新 100 条，必要时使用官方 `before` 游标向前补页，覆盖窗口已加载的区间，并为最早原生用户行补充可完整核对的记录；避免只拼最新一页而漏掉中间消息。每页最多 100 条，合计最多 200 页/20000 条、消息响应累计 8 MiB，renderer 请求窗口合计 4.5 秒；只通过完整行的角色、正文、附件与相邻行 ID 唯一匹配未回填的原生 `dbId`，不拿截断为前 240 个字符的 summary 当作全文。摘要 ID 仅用于检查历史覆盖。达到尺寸、页数或时间边界会保留原窗口内容，超范围长会话不能保证即时刷新，可在天工重新打开任务读取已保存记录。

天工接入页启动按钮下方持续显示“桌面对话同步”，随已有 dashboard 刷新，不增加 GUI 主线程网络操作；概览的 Harness 详情也附带该状态。状态仅保留固定文案、类型和检查时间，30 秒以内显示上次结果，过期不继续宣称窗口已更新。明确区分能力已准备、消息已保存待更新、实际更新、任务未打开、原生忙/未保存/匹配不明、读取失败与超限；能力检查成功不再等同于消息已更新，`/json/list` 可用也不再单独表示同步能力已就绪。超出页数/尺寸限制退出当前刷新排队，后续新保存或恢复可重新排队，避免无进展地每 5 秒反复读同一超限历史。普通忙碌/暂时失败继续重试展示，不重放任务。

常规每轮不再单独发送永久留在聊天里的“正在等待天工 Claw 处理…”；仅在支持更新的消息通道显示临时准备/处理状态，最终答复、审批或错误会收尾，详见下文。队列满、排队超时、审批和实际错误仍明确回复。Hub 重启后排队和诊断不持久恢复，重新选择历史时从已核对关联加载自有回复 ID 并排队；正文仍在天工官方记录。旧版未登记来源的缓存占位不能据其文案猜测为 Hub 行，更早来源迁移阶段需正常退出天工，再从 Hub 打开一次读取已保存内容；此前作用域修复中，已经完成来源迁移并启用通道的实例仅需更换 Hub；旧实例已继承监听的情况另需一次正常退出迁移，之后仍无需每轮重启。回退已发布 `v0.4.30-3` 会恢复固定版本/资源门槛；回退更早版本可能移除整个适配，数据和模型配置保留，已启动天工不自动关闭。关键代码见 [同步适配](../../src/gmclaw_runtime/display.rs)、[setup 能力检查](../../src/gmclaw_runtime/display-setup-schema.js)、[能力检查](../../src/gmclaw_runtime/display-schema.js)、[启动/刷新队列](../../src/gmclaw_runtime.rs) 和 [IM 保存及回复](../../src/gmclaw_im.rs)。

### 原生会话执行步数兼容

2026-10-06 用户再次反馈“原会话执行步数无效，未恢复”。只读核对天工 1.1.1 官方安装源码确认：桌面普通聊天和网页任务都发送 `max_steps=1000`；Harness 缺省值为 `20`，没有 `200` 的原生上限。此前 Hub 把新建配置的 `1–200` 限制用于原生历史，导致已通过状态核对的正常桌面会话仍无法绑定。

本轮把历史恢复、会话元数据登记及 Harness 请求统一为 Hub 的原生兼容范围 `1–1000`，保留原值并传入后续任务，不静默压缩为 `200`。原生元数据缺少该字段时沿用官方默认 `20`；确实没有元数据的空会话沿用 Hub 新建配置。Hub 的 `gmclawBridge.maxSteps` 仍默认 `30`、允许 `1–200`，不因兼容历史而提高新建会话的默认预算。`1000` 是已核对桌面版本的实际提交值和本轮兼容边界，不宣称是官方协议的硬上限；`0` 不代表不限步数，非整数、负数及超出兼容范围仍拒绝恢复或提交。

### 恢复时的状态判断

天工 1.1.1 的 `sessions.status` 是持久运行记录，不是原子的实时会话状态。官方 Harness 在准备每轮请求时写入 `processing`，发出 `over` 后才更新结束状态；桌面收到 `over` 时主动中止流，因此正常结束的会话也可能保留 `processing`，重启天工不会统一清除此字段。旧判断会出现“未绑定会话，操作未完成：天工会话正在执行或等待审批，请先在桌面处理”。这里“未绑定”表示恢复被前置核对阻止，不等于自动连接授权丢失。核对要求元数据返回明确的 `message_count`，并与实际事件数量一致；字段缺失、数量不符时拒绝本次操作，不把缺失字段当作空会话。

- 会话事件按真实行 `id` 排序，而不是每轮重复的 `message_index`。正常结束证据要求最后一轮有真实 `harness_sidecar` 用户事件，其后有 `over`，末尾仍为该终态，并且本轮没有 `confirm`。有新用户事件而无结束事件时，即使元数据写着 `completed`，也拒绝恢复。
- 最后一轮包含 `confirm` 时仍视为待处理，不以同轮 `over` 或 `completed` 清除审批。批准、拒绝会开启新轮次，只有后续轮次完整结束且不再含 `confirm` 才能作为恢复证据；较新的用户事件本身不能证明旧审批已经解除。
- 仅对 `processing` 提供残留状态例外：上述结束证据成立，当前轮次 `chat_id` 存在且非空，`metadata.updated_at` 不晚于结束事件的 `created_at`，并在至少 1 秒后二次读取时元数据（含 `chat_id`）和全部事件保持一致。任一读取失败、轮次身份缺失、时间不能核对或快照变化均拒绝本次操作，保留原会话。判断全程只读，不把官方 `status` 改写成 `completed`。
- `running`、`awaiting_confirmation`、未知状态以及 Hub 关联文件中的待审批/未知标志继续拦截；原当前会话中未过期、同连接与同运行实例的审批码仍沿用现有批准/拒绝流程，不因恢复校验自动授权。确实空的原生任务沿用空会话登记及模型选择规则。

官方没有可原子读取每个会话当前执行状态的接口，`/ctrl/status` 中恒为空的 `current_session` 不能证明空闲。至少 1 秒间隔的稳定快照缩小新请求准备与首条事件落盘之间的并发窗口，但不会获得桌面锁；执行前仍重新核对状态，读取不足时不放行，不用模型请求探测，也不重放原任务。关键实现为 [真实桌面状态核对](../../src/gmclaw_im/desktop.rs) 与 [数据接口及时间字段](../../src/gmclaw_desktop.rs)。

### Hub 会话关联文件

关联文件位于 Hub 配置文件旁，使用 `with_extension("gmclaw-sessions.json")` 命名；例如配置为 `<目录>/config.toml` 时为 `<目录>/config.gmclaw-sessions.json`。文件版本为 `1`，记录真实会话与任务 ID、标题、精确模型 ID/名称、配置指纹、项目身份/目录、桌面用户身份、执行步数及待审批/未知标志。可选 `context.owned_reply_ids` 只记录 Hub 已成功通过官方 `system` 插入返回的最近 128 个去重正数行 ID（不超过 JS 安全整数 `9007199254740991`），缺失默认为空，空值不输出；读写时验证范围/数量，仍受整个关联文件 8 MiB/20000 条限制。插入后额外关联保存为最佳努力，失败不阻止本已授权的模型执行；原先必要的未知/终态记录流程保留。恢复这些来源前核对任务、会话与原生用户/项目记忆身份，不用行 ID 放宽执行或审批保护。它不保存运行口令、模型 Key、审批码、工具参数或对话正文；正文由天工数据服务保存。

旧关联缺少新字段继续兼容，不给旧消息猜补来源。旧 Hub 可忽略新字段，但其重写关联会丢失新增 ID；回退后再升级时可能需要正常重开天工一次清除无来源的旧窗口缓存。展示不明时原生缓存仍保留，不能把它当作执行失败或批准重放。

读取和写入使用同一进程内 IO 锁，锁等待与文件处理合计最多等待 5 秒，限制 8 MiB 和 20000 个关联；写入通过同目录临时文件、同步后原子替换。锁随实际后台文件操作保留，即使调用端超时，后台操作仍持有锁直到 IO 结束，不会让仍在完成的操作与下一次保存交错。超时需核对记录；这不是跨进程锁或多实例同时编辑的承诺。格式/版本不符时明确报错，不自动抹去记录。待审批仅保留不可自动恢复的标志，Hub 重启后原确认码不会重新可用。

上一阶段在 Hub 内存里创建、没有真实桌面任务的会话不能凭空迁移成完整桌面对话。本轮不查找私有日志重建正文；仍保留旧内存会话状态保护，但继续执行会提示新建真实桌面会话。已经成功登记的任务与关联可在后续 Hub 启动后重新选择，固定模型不会因天工默认模型改变而漂移。

## 执行、事件与审批

执行器按天工 1.1.1 的 `prefix|JSON` 行事件读取 `text`、`confirm` 和 `over`，处理跨网络分块和 UTF-8 边界；这不是 Codex remote-control JSON-RPC，也不是普通 `data:` SSE。Hub 发送答复或审批消息，普通每轮不再额外发送固定等待文字；本轮临时回复状态使用独立更新/终态路径，队列满、超时与错误仍明确回复，不把任意工具进度载荷直接公开到 IM。

每次请求显式使用 `tool_execution_mode=confirm`，Hub 不自动批准工具。是否需要审批由天工自身工具策略决定，`confirm` 不表示每个工具都必须确认；只有 Harness 返回待确认事件时才进入 IM 审批。收到该事件后，Hub 展示工具名和完整 JSON 参数，生成独立请求标识和兼容用的 12 位确认码，15 分钟内有效。一次最多展示 16 个工具、合计 24 KiB 的审批说明；超过展示边界就拒绝在消息中批准，不截断参数后继续授权。批准和拒绝只包含该轮记录的调用 ID，不提供自动批准全部未来工具、跨发送者审批或逐个工具选择。

### 准备回复与终态

天工请求通过基础文字/审批检查后、准备进入排队时建立独立回合标识；飞书显示与 Codex 相同布局的“正在准备回复”卡，实际准备完成、即将提交 Harness 后更新为“正在处理”。最终答复更新同一张卡，并移除“生成中”；不另留一条每轮固定等待文字。出现工具审批时结束生成态，改为审批提示及已有本轮答复，再发送独立审批控件；失败、队列拒绝、排队/执行超时也更新为明确终态。

企业微信只有本次普通消息含有效 `Message` 回调时才使用其原生 `reply_stream`：同一随机 stream ID 从 `finish=false` 转为 `finish=true`；审批卡回调不冒充普通消息回调。没有该能力时直接投递最终文字。微信没有可编辑/撤回的等待卡，继续投递答复、错误与审批文字，不发送无法去除的每轮等待句；Telegram 本轮不接天工。这里新增准备/处理状态，不宣称天工答复已成为逐字流式输出，也不变更模型协议。

飞书序列化卡超过 24 KiB 或最终卡更新失败时，先按无损 Unicode 分段发送当前可投递答复，再把已有卡更新为“已回复”或“投递未确认”的完成态；不先撤除状态而丢失答复。企业微信完整答复超过原流式通道的 20 KiB 边界或更新失败时，同样先发送文字再结束原 stream。答复继续沿用原最多 16000 字及截取提示，完整天工记录由桌面保存；文本 fallback 保留这段可投递答复的空白和内容。每次新展示 API 请求最多 10 秒，失败不会重放模型/工具。

`TurnDisplayGuard` 将准备、处理中与收尾载荷按同一 outbound 队列顺序投递；随机回合同时绑定平台/账号/聊天/发送者、会话、配置指纹和本轮回调，群聊多人不会共用一张状态卡。状态位于独立 worker 中，最多 128 个活动回合、256 个已完成卡片回合标识，约每 15 秒清理，展示 TTL 为 20 分钟；不写 Codex runtime、TOML 或关联文件。异常返回或任务 future 取消时，guard 的 `Drop` 仅收尾为“状态未确认”，不声称停止、不再次执行请求。投递前复核允许名单和配置，变更后不展示答复正文，已有状态只尝试固定说明；微信正常、无 token 备用及上下文恢复都保留原回合身份，在每段正文发送前核对最新允许名单、账号启用和连接配置；变化后停止未发段落，已发内容无法撤回。上下文恢复可能重复已送前缀，普通网络失败不保证投递，不新增模型或业务重试。

最终正文或等待卡的终态更新失败时，只有已经确认归属的原飞书消息 ID、或本轮确定的企微 callback/stream ID，才保留独立 `closing` 记录。它只保存固定“已回复，见随后文字”“投递未确认”或权限/配置变化说明，不保存或重发正文；已完成回合继续去重，后续“处理中”不能覆盖该终态。约每 15 秒只更新同一个原控件，最多 3 次额外尝试、最长保留至该回合 20 分钟 TTL；账号禁用期间不发送、不消耗尝试次数，仍在 TTL 内重新启用时可继续。每次重试再核权，变化后只用固定说明；无已知回执不创建替代卡，也不重发文字、模型或工具。达到次数/期限后停止，失败保留脱敏诊断，不增加跨 Hub 重启的持久控件恢复。每次清理先直接移除已过 TTL 的 closing，最多发起 2 个终态更新、优先较早回合；错过的 tick 跳过，不将平台不可用积累成整批串行超时。

平台不可用、账户停用、响应回执丢失或直接终止 Hub 时，无法保证聊天中的旧卡实际更新；支持的终态路径会尝试收尾，失败不影响已保存桌面结果或执行保护。响应超时后的文字 fallback 可能与已送达的卡重复显示同一答复，不触发第二次模型/工具执行。回退旧 Hub 会失去这套临时状态，新状态不会跨 Hub 重启持久恢复；替换前仍须在天工核对当前任务/审批。关键代码见 [独立回合与 guard](../../src/im/core/executor_turn.rs)、[outbound worker](../../src/im/core/outbound.rs)、[天工执行入口](../../src/gmclaw_im.rs) 和 [现有飞书生成/完成布局](../../src/im/feishu/renderer/streaming/reply.rs)。

### 按当前平台处理审批

| 平台 | 操作方式 | 完整参数与投递失败 |
| --- | --- | --- |
| 飞书 | 复用原审批卡布局，点击「批准全部」或「拒绝全部」，处理本轮列出的全部调用 | 卡片显示工具名称及完整参数；序列化卡片超过 24 KiB 时先分段发送参数全文，再发简短说明和按钮；卡片投递失败时回退完整文字与兼容命令 |
| 企业微信 | 复用原审批按钮，点击「批准全部」或「拒绝全部」 | 先分段发送完整工具参数文字，再发送关联该轮请求的按钮卡；全文未投递完成时不发送按钮，不以截断参数代替全文 |
| 微信 | 沿用 Codex 现有文字选项，按提示回复 `/1` 批准全部或 `/2` 拒绝全部；兼容 `1`/`2` 与 `y`/`n` | 微信没有新增审批按钮；仅在当前天工待审批状态把这些选项解释为该轮决定 |

审批卡使用独立天工 callback，不复用 Codex 的待审批记录或提交入口。每个请求通过随机标识隔离，并同时绑定 `SenderKey`（平台、Hub 账号、聊天 ID、发送者 ID）、当前天工会话、连接配置指纹和产生该审批时的运行授权/桌面实例身份。只有对应发送者在原聊天、天工模式和原会话内可以处理；其他发送者、不同账号/聊天、非法选项索引、过期卡、重复点击、已切执行端或 Hub/天工重启后的旧卡均不能执行，也不能落入 Codex 审批路径。允许名单与群提及等原有权限校验继续生效，群内卡片的可见性仍由平台控制。

按钮、微信选项和旧 `/tg approve <确认码>`、`/tg reject <确认码>` 共用当轮批准/拒绝预检和一次性消费。卡片回执说明已选择并提交处理，执行是否完成以随后任务结果为准，不把点击成功当成工具完成。卡片或完整说明投递失败不会自动授权；兼容命令仍要求同一有效审批身份。消息存储前的连接、目录、模型或桌面状态等可恢复预检失败会保留待审批，可继续操作当前仍有效的卡片；过期或运行身份变化的旧审批不能继续。桌面记录准备之后、消费之前再次检查允许名单、配置、有效期与运行身份；消息记录或执行进入可能产生写入的阶段后，失败按未知状态处理，不能通过重复点击或补发命令重放。不新增永久授权、单个工具勾选或跨轮批准。

### 执行保护

首版只支持父会话工具审批。携带 `run_id` 或 `child_session_id` 的子 Agent 审批需要不同的续执行协议，当前拒绝在 IM 中处理并提示回天工桌面确认，不把子 Agent 调用 ID 填入父会话 `confirm_action`。

每次提交任务前先核对连接状态，只有授权和组件就绪才发送请求；完整检查最多等待 18 秒，调用端保留 1 秒调度余量。已启用的接入会自动重新识别变化后的运行授权，不要求再次 `/tg`。实际目录/请求体、固定模型与桌面任务状态的校验在消费审批、标记执行中之前完成。连接尚未就绪、目录或模型不可用、桌面正在执行时，本条任务不提交，原会话与审批保留；不把这种前置失败误标为工具执行未知。消息存储及执行进入可能产生写入的阶段后，失败按未知状态处理，不能重放来补展示。

工具审批同时绑定当轮运行授权与桌面主进程身份，天工重启后即使固定启动口令相同，也不会把旧审批交给新实例。自动连接及 `/tg` 都不批准或重放原任务。此时先在天工核对旧任务，再显式 `/tg new` 将旧会话归档为状态未知，旧调用 ID 不发送给新实例。临时授权缓存不进入会话配置指纹，因此识别手动实例本身不会改写已保存设置或替换闲置会话的目录与模型。

同一发送者一次只能执行或等待一个请求；全局同时向 Harness 提交一个请求，容量为 1 个执行和最多 32 个等待名额。等待执行槽最多 30 秒，超时消息未提交天工，用户需重新发送。单次执行等待最多 15 分钟，连接超时 5 秒、读取空闲超时 300 秒；排队后还会重新检查配置和审批有效期。单条普通文字最多 128 KiB，过旧消息拒绝执行。

解析器限制单条事件与累计文字为 4 MiB、整体响应为 16 MiB；缺少 `over`、空结束结果、流中断、错误或超限均按失败处理。普通最终答复最多向 IM 发送 16000 个 Unicode 字符，超出时明确提示已截断并到天工桌面查看；工具审批不使用这种截断规则。

Harness 调用不自动重试：网络中断时工具可能已执行。超时、流中断或配置变化后的执行状态会标记为未知，后续消息不会自动重放该任务。未知状态阻止 `/q` 和跨执行端退出；用户先到天工桌面确认结果，再显式 `/tg new` 将旧会话归档为不可恢复并新建，回复会说明没有停止旧任务。

同一连接且未过期的待审批必须先批准或拒绝，不能用新建会话跳过。审批已过期或连接配置已变化时，显式 `/tg new` 清除不能再提交的旧确认码，把旧会话按未知状态归档；绝不把旧调用 ID 发送到新连接。显式 `/tg new` 会在原运行/审批保护之后尝试自动准备连接，再进入共有新建设置；只有提交创建动作后才创建新会话。准备失败不会批准旧工具或停止旧任务，必须按消息说明处理后重试。

`/s`、关闭连接、切换模式或新建会话均不证明天工工具已取消，当前没有独立取消能力。

## 回滚与维护定位

在没有运行任务或待审批时，发送 `/gpt`（兼容 `/gmclaw off`）返回 Codex。维护时停用 `gmclawBridge.enabled` 会阻止普通新文字执行，但后续允许的显式 `/tg` 会重新自动准备接入；要持续限制外部使用，应调整原有 IM 账号与允许名单。模型条目与外部执行连接独立，模型备份恢复不回滚授权或会话目录。

本轮增加配置文件旁的 `.gmclaw-sessions.json` 关联文件及天工官方数据服务中的任务/消息写入，没有改变 Hub TOML 字段格式。维护或回退前应保留 Hub 配置、关联文件和天工自身数据的备份；旧版不会读取这些新增关联，回退不会自动删除已登记的桌面任务。不要通过删除关联文件解除未确认任务：这会丢失精确模型绑定与待审批/未知标志，却不能停止天工中的操作。关联文件格式损坏或版本变化时先保留原件，再核对桌面结果，不自动重建或清空。天工数据库与任务正文仍由天工维护，Hub 不提供本轮写入的自动回滚。旧 Hub-only 会话正文不会因升级或回退自动补到桌面。

此前自动授权阶段新增可选 `desktopPath`，旧配置缺失时按自动查找兼容；`authToken` 沿用原字段，自动生成不改变格式。GUI 桥接表单已在上一阶段移除，旧字段仍保留；本轮 `projectPath` 可用作新会话默认目录，最终目录和模型分别保存在会话中。恢复旧版时需重新核对旧程序要求的固定目录。旧程序不会自动注入口令，且再次保存可能丢弃不认识的 `desktopPath`，回退前先备份；需要旧版外部消息时仍由用户在天工启动环境提供与 Hub 相同的 `GMCLAW_AUTH_TOKEN`。关闭 Hub 或停用桥接不会结束已启动的天工桌面或其中任务。回到已发布 `v0.4.30-2` 程序会丢失本次运行的模式/历史索引，恢复旧 `/gmclaw` 命令行为，不再提供新增短指令和文字菜单；不会停止天工已经收到的任务。替换程序前仍需在对应执行端确认任务与审批状态，避免将重启误当成取消。

本次历史恢复状态及执行步数修复不新增 TOML 字段，不迁移关联文件版本，不重置天工官方会话状态或用户配置。回退到前一桌面同步版本仍能读取原关联记录，但残留 `processing` 或原生 `1000` 步可能再次阻止恢复；不能通过手动清空未知/审批标志代替核对桌面结果。显式桌面启动按钮的配置准备与回滚另见上文使用说明。

本轮审批交互不新增 TOML 或关联文件字段，审批请求/随机标识仍仅在 Hub 内存，不持久恢复可点击控件。回退程序后按旧版长命令处理新产生的审批，当前按钮或文字选项不会跨程序恢复；替换前应在对应桌面核对现有任务，程序重启不代表批准、拒绝或停止工具。

天工审批使用独立的参数分段：微信保留长 JSON 字符串内的空白，正常投递与上下文过期后的文字恢复使用同一路径；飞书与企微同样保留完整参数。新增审批的传输诊断不记录正文、请求键或备用确认码，飞书审批专用 API 响应只记操作、HTTP 状态与错误码，避免平台回显卡片内容进入诊断。这里限定本轮新审批传输，不改变原 Codex 日志约定。

文字说明已部分送达后再遇到微信上下文失效，恢复投递仍可能重复发送先前的说明；平台响应超时也可能重复投递卡片或文字。它们使用同一个审批请求，重复投递不重新调用模型或工具，重复按钮仍按当前待审批核对；真实投递和恢复表现待用户验收。
